# Kiro Project Setup Prompt (Migration-Aware)
# ============================================
# Copy and paste this prompt into a new or existing project to set up
# a professional Python development environment with Kiro-native configuration.
# 
# MIGRATION MODE: This prompt is designed to work with both new AND existing projects.
# It will detect existing configurations and MERGE them with the standard setup,
# preserving project-specific customizations while adding missing standard components.
#
# This prompt replaces Cline rules (.clinerules) and Amazon Q rules (.amazonq)
# with Kiro steering files, hooks, and MCP server configuration.

---

## CRITICAL: MIGRATION-AWARE EXECUTION

This prompt MUST be executed in migration-aware mode. For EVERY step:

1. **DETECT**: Check if the target file/directory already exists
2. **ANALYZE**: If it exists, analyze its current content for project-specific customizations
3. **MERGE**: Combine existing customizations with the standard template
4. **PRESERVE**: Never delete or overwrite project-specific configurations
5. **REPORT**: Document what was preserved, what was added, and any conflicts found

When conflicts arise between existing config and standard template:
- **PRESERVE existing** project-specific settings
- **ADD missing** standard settings
- **FLAG conflicts** for user review
- **DO NOT silently overwrite** any existing configuration

## PART 1.5: VIRTUAL ENVIRONMENT SETUP (MANDATORY)

Before proceeding with any further setup steps, ensure the virtual environment exists and is functional.

### Steps:
1. Check if `venv/` directory exists
2. If `venv/` does NOT exist:
   - Create it: `python -m venv venv`
   - Activate it:
     - Windows: `venv\Scripts\activate`
     - Linux/Mac: `source venv/bin/activate`
   - Install all required packages: `pip install -e ".[dev,cdk]"`
3. If `venv/` exists:
   - Verify it's functional: `venv/Scripts/python --version` (or `venv/bin/python`)
   - Activate it
   - Ensure dependencies are current: `pip install -e ".[dev,cdk]"`

4. After venv is ready, install the pre-commit git hook:
   - Run: `bash scripts/setup-hooks.sh`
   - This generates `.git/hooks/pre-commit` with the absolute venv path
   - See Part 1.6 for details on the pre-commit hook pattern

This step MUST complete successfully before any subsequent parts execute. All later steps assume an activated venv.

## PART 1.6: PRE-COMMIT HOOK SETUP (PROJECT-LOCAL, VENV-BOUND)

This section sets up a project-local pre-commit hook that runs fast linting checks (ruff lint + ruff format) on every `git commit`. The hook is venv-bound — it uses the absolute path to the project's venv `pre-commit` executable, avoiding all PATH resolution issues and cross-project interference.

### Why This Pattern

- Standard `pre-commit install` writes a hook that relies on the system PATH, which breaks when multiple Python projects share the same machine or when the IDE doesn't include the venv in PATH.
- This pattern hardcodes the absolute venv path in the git hook, so it works regardless of how git is invoked (terminal, IDE, GUI client).
- Only fast checks (ruff) run in the hook. Slow checks (mypy, pytest, bandit) are left for CI or manual invocation.

### Migration Behavior:
- If `.pre-commit-config.yaml` exists, READ it first and PRESERVE all existing hooks and configurations
- Only ADD missing standard hooks (ruff, ruff-format)
- If `scripts/setup-hooks.sh` exists, PRESERVE it (it may have project-specific customizations)
- If `.git/hooks/pre-commit` exists, do NOT overwrite it — the developer may have customized it
- Report what was preserved vs created

### Step 1: Create `.pre-commit-config.yaml` (if it doesn't exist)

This file defines ALL available hooks. The git hook script selectively runs only the fast ones.

```yaml
repos:
  # Fast linting and auto-fix (runs in pre-commit hook)
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.4.0
    hooks:
      - id: ruff
        args: [--fix]
        exclude: ^(old/|workspace/|tmp/|venv/)
      - id: ruff-format
        exclude: ^(old/|workspace/|tmp/|venv/)

  # Type checking (available but NOT run in pre-commit hook — too slow)
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.17.0
    hooks:
      - id: mypy
        args: [--ignore-missing-imports]
        exclude: ^(test/|old/|workspace/|tmp/|venv/|scripts/)
        additional_dependencies: [types-requests, types-python-dateutil]

  # Test suite (available but NOT run in pre-commit hook — too slow)
  - repo: local
    hooks:
      - id: pytest
        name: pytest
        entry: pytest
        language: system
        args: [--cov=src, --cov-fail-under=80]
        pass_filenames: false
        always_run: true
```

If `.pre-commit-config.yaml` already exists:
- PRESERVE all existing repos and hooks
- ADD the ruff-pre-commit repo if no ruff hooks are configured
- PRESERVE existing `exclude` patterns (they are project-specific)
- PRESERVE existing `rev` pins (they may be intentionally pinned)

### Step 2: Create `scripts/setup-hooks.sh` (if it doesn't exist)

This script generates the `.git/hooks/pre-commit` file with the absolute venv path for the current developer's machine. It must be run once per clone.

```bash
#!/usr/bin/env bash
# scripts/setup-hooks.sh — Installs project-local pre-commit hook
# Uses absolute venv path to avoid PATH issues across multiple projects
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_ROOT="$(dirname "$SCRIPT_DIR")"

# Detect OS and set venv pre-commit path
if [[ "$OSTYPE" == "msys" || "$OSTYPE" == "cygwin" || "$OSTYPE" == "win32" ]]; then
    PRECOMMIT_PATH="$PROJECT_ROOT/venv/Scripts/pre-commit.exe"
else
    PRECOMMIT_PATH="$PROJECT_ROOT/venv/bin/pre-commit"
fi

# Verify pre-commit exists in venv
if [ ! -x "$PRECOMMIT_PATH" ]; then
    echo "ERROR: pre-commit not found at $PRECOMMIT_PATH"
    echo "Run: pip install -e '.[dev]' in your activated venv first"
    exit 1
fi

# Write the git hook
cat > "$PROJECT_ROOT/.git/hooks/pre-commit" << HOOK
#!/usr/bin/env bash
# Auto-generated by scripts/setup-hooks.sh — do not edit manually
# Pre-commit hook using absolute venv path to avoid PATH issues
# Only runs fast checks (ruff lint + format), not mypy/pytest

PRECOMMIT="$PRECOMMIT_PATH"

if [ ! -x "\$PRECOMMIT" ]; then
    echo "ERROR: pre-commit not found at \$PRECOMMIT"
    echo "Recreate venv: python -m venv venv && pip install -e '.[dev]'"
    exit 1
fi

# Run ruff linting (with auto-fix)
"\$PRECOMMIT" run ruff --config .pre-commit-config.yaml
RUFF_RESULT=\$?
if [ \$RUFF_RESULT -ne 0 ]; then
    exit \$RUFF_RESULT
fi

# Run ruff formatting check
exec "\$PRECOMMIT" run ruff-format --config .pre-commit-config.yaml
HOOK

chmod +x "$PROJECT_ROOT/.git/hooks/pre-commit"
echo "Pre-commit hook installed successfully."
echo "Hook points to: $PRECOMMIT_PATH"
```

### Step 3: Run the setup script

After the venv is set up and dev dependencies are installed (Part 1.5), run:

```bash
bash scripts/setup-hooks.sh
```

This generates `.git/hooks/pre-commit` with the absolute path to the current machine's venv. This file is NOT checked into git (`.git/hooks/` is untracked by design) — each developer generates their own by running the setup script.

### Step 4: Update README.md

Add the following to the development setup instructions in README.md (merge with existing content):

```markdown
### Git Hooks Setup

After installing dev dependencies, set up the pre-commit hook:

```bash
bash scripts/setup-hooks.sh
```

This installs a git hook that runs ruff linting and formatting checks on every commit. The hook uses the project's virtual environment directly, so it works regardless of your shell PATH configuration.
```

### Key Design Decisions:
1. **Absolute venv path in hook**: Avoids all PATH resolution issues. Works regardless of how git is invoked.
2. **Selective hook execution**: `.pre-commit-config.yaml` defines all hooks, but the git hook only runs the fast ones (ruff lint + format). Keeps commits fast.
3. **Hook is NOT checked into git**: `.git/hooks/` is untracked. Each developer generates their own hook with their own absolute path via the setup script.
4. **Fail-fast on missing venv**: The hook checks for the pre-commit executable and gives a clear error with recovery instructions.
5. **pre-commit as venv dependency**: Listed in `pyproject.toml` under dev deps, installed automatically with `pip install -e ".[dev]"`.

### What runs where:
| When | What runs | Why |
|------|-----------|-----|
| Pre-commit hook | ruff lint + ruff format | Fast (<1s), catches most day-to-day issues, auto-fixes |
| CI pipeline | ruff + mypy + pylint + bandit + pytest | Full validation, acceptable to be slower |
| Manual (optional) | `pre-commit run mypy` | Developer can opt-in to type checking before push |

## PART 4: LEGACY DEPENDENCY MIGRATION

This section handles migration from legacy dependency management formats to the modern pyproject.toml standard. This migration is CRITICAL for aligning with Python packaging best practices.

### Detection Phase

Check for the following legacy dependency management files:

| File Pattern | Format | Priority |
|--------------|--------|----------|
| `requirements.txt`, `requirements-*.txt`, `*-requirements.txt` | pip requirements | High |
| `setup.py` | setuptools (legacy) | High |
| `setup.cfg` | setuptools (declarative) | High |
| `Pipfile`, `Pipfile.lock` | pipenv | Medium |
| `pyproject.toml` with `[tool.poetry]` | poetry | Medium |
| `environment.yml`, `environment.yaml` | conda | Low |
| `pyproject.toml` with `[tool.flit]` | flit | Low |

### Migration Decision Tree

```
IF pyproject.toml exists with [project.dependencies]:
    → Already using modern format, MERGE standard deps only
ELSE IF any legacy format exists:
    → Perform FULL MIGRATION to pyproject.toml
ELSE (new project):
    → Create fresh pyproject.toml with standard structure
```

### Requirements.txt Migration

#### File to Section Mapping

| Source File | Target Section | Install Command |
|-------------|----------------|-----------------|
| `requirements.txt` | `[project.dependencies]` | `pip install .` |
| `requirements-prod.txt` | `[project.dependencies]` | `pip install .` |
| `requirements-dev.txt` | `[project.optional-dependencies.dev]` | `pip install ".[dev]"` |
| `dev-requirements.txt` | `[project.optional-dependencies.dev]` | `pip install ".[dev]"` |
| `requirements-test.txt` | `[project.optional-dependencies.test]` | `pip install ".[test]"` |
| `test-requirements.txt` | `[project.optional-dependencies.test]` | `pip install ".[test]"` |
| `requirements-cdk.txt` | `[project.optional-dependencies.cdk]` | `pip install ".[cdk]"` |
| `requirements-docs.txt` | `[project.optional-dependencies.docs]` | `pip install ".[docs]"` |
| `requirements-{custom}.txt` | `[project.optional-dependencies.{custom}]` | `pip install ".[{custom}]"` |

#### Parsing Rules

1. **Preserve exact version pins**: Keep `==`, `>=`, `<=`, `~=`, `!=` exactly as specified
2. **Preserve all dependencies**: Include transitive dependencies (do not filter)
3. **Handle -r includes**: Parse included files, but avoid duplicating deps in target
4. **Handle environment markers**: Preserve markers like `; python_version >= "3.9"`
5. **Handle comments**: Ignore lines starting with `#`
6. **Flag for manual review**:
   - `-e` editable installs (local paths)
   - `--index-url`, `--extra-index-url` (move to pip.conf or document)
   - Local wheel files (`.whl`)
   - Git URLs (`git+https://...`)

#### Example Migration

**Before:**
```
# requirements.txt
boto3==1.28.0
requests==2.31.0

# requirements-dev.txt
-r requirements.txt
pytest==7.4.0
black==23.7.0
hypothesis==6.82.0

# requirements-cdk.txt
aws-cdk-lib==2.100.0
constructs==10.2.0
```

**After (pyproject.toml):**
```toml
[project]
dependencies = [
    "boto3==1.28.0",
    "requests==2.31.0",
]

[project.optional-dependencies]
dev = [
    "pytest==7.4.0",
    "black==23.7.0",
    "hypothesis==6.82.0",
]
cdk = [
    "aws-cdk-lib==2.100.0",
    "constructs==10.2.0",
]
```

### setup.py Migration

#### Extraction Strategy

1. **Try static analysis first** (AST parsing of setup.py)
2. Extract from `setup()` call:
   - `name` → `[project] name`
   - `version` → `[project] version` (or dynamic if from file)
   - `description` → `[project] description`
   - `author`, `author_email` → `[project] authors`
   - `url` → `[project.urls]`
   - `python_requires` → `[project] requires-python`
   - `install_requires` → `[project.dependencies]`
   - `extras_require` → `[project.optional-dependencies]`
   - `entry_points` → `[project.scripts]` or `[project.entry-points]`
3. If static analysis fails, flag for manual review

### setup.cfg Migration

#### Section Mapping

| setup.cfg Section | pyproject.toml Section |
|-------------------|------------------------|
| `[metadata] name` | `[project] name` |
| `[metadata] version` | `[project] version` |
| `[metadata] description` | `[project] description` |
| `[metadata] author` | `[project] authors` |
| `[options] python_requires` | `[project] requires-python` |
| `[options] install_requires` | `[project.dependencies]` |
| `[options.extras_require]` | `[project.optional-dependencies]` |
| `[options.entry_points]` | `[project.scripts]` |

### Pipfile Migration

#### Section Mapping

| Pipfile Section | pyproject.toml Section |
|-----------------|------------------------|
| `[packages]` | `[project.dependencies]` |
| `[dev-packages]` | `[project.optional-dependencies.dev]` |
| `[requires] python_version` | `[project] requires-python` |

**Note**: Use `Pipfile.lock` for exact versions if available (more accurate than Pipfile).

### Poetry pyproject.toml Migration

If `pyproject.toml` exists with `[tool.poetry]` sections, reformat to PEP 621 standard:

| Poetry Section | Standard Section |
|----------------|------------------|
| `[tool.poetry] name` | `[project] name` |
| `[tool.poetry] version` | `[project] version` |
| `[tool.poetry.dependencies]` | `[project.dependencies]` |
| `[tool.poetry.group.dev.dependencies]` | `[project.optional-dependencies.dev]` |
| `[tool.poetry.group.{name}.dependencies]` | `[project.optional-dependencies.{name}]` |
| `[tool.poetry.scripts]` | `[project.scripts]` |

**Note**: Remove `[tool.poetry]` sections after migration. Keep `poetry.lock` for reference but it won't be used.

### Conda environment.yml Migration

#### Handling Strategy

1. Parse `dependencies:` list
2. Separate pip dependencies (under `- pip:` subsection) from conda dependencies
3. Migrate pip dependencies directly to `[project.dependencies]`
4. **Flag conda-only packages** for manual review (may need pip equivalents)
5. Warn about potential package name differences between conda and pip

### Documentation Updates (REQUIRED)

After migrating dependencies, update ALL documentation that references the old format:

#### Files to Update

1. **README.md**: 
   - Change `pip install -r requirements.txt` → `pip install .`
   - Change `pip install -r requirements-dev.txt` → `pip install ".[dev]"`
   - Update development setup instructions

2. **CONTRIBUTING.md** (if exists):
   - Update installation instructions
   - Update development environment setup

3. **docs/forLLMConsumption.md**:
   - Update dependency management section
   - Document new install commands

4. **docs/*.md** (all documentation):
   - Search for `requirements.txt` references and update

5. **CI/CD workflows** (`.gitlab-ci.yml`, `.github/workflows/*.yml`):
   - Change `pip install -r requirements.txt` → `pip install -e .`
   - Change `pip install -r requirements-dev.txt` → `pip install -e ".[dev]"`

6. **Makefile** (if exists):
   - Update install targets

7. **Docker files** (if exist):
   - Update pip install commands

### Cleanup (After Successful Migration)

After verifying the migration is complete and working:

1. **DELETE legacy files** (version control provides backup):
   - `requirements*.txt` files
   - `setup.py` (if fully migrated)
   - `setup.cfg` (if fully migrated)

2. **DO NOT DELETE**:
   - `pyproject.toml` (this is the target!)

# Coding Standards (NO EXCEPTIONS)

1. **JSON Field Access**: Use string constants, not literals
   - BAD: `obj["content"]`

2. **OOP Design**: Use abstractions and interfaces to avoid duplication
   - Group related classes in a module (Pythonic convention per PEP 8)
   - Use separate files for large or unrelated classes
   - Inheritance visible from class/file names

3. **Modular Functions**: Break down into reusable library-style functions

4. **Absolute Imports**: All imports must use absolute paths. If path issues arise, resolve them by modifying the Python path (e.g., `sys.path` manipulation in entry points, or proper package configuration in `pyproject.toml`). Do NOT use relative imports.

6. **Named Parameters**: Always use named parameters at call sites
   - BAD: `f(5, "abc")`
   - GOOD: `f(a=5, b="abc")`

7. **Error Handling**: 
   - Throw exceptions for errors (not empty lists/zero values)
   - Return `None` for expected failures
   - Custom exceptions with `details=None` default

8. **Exception Hierarchy**: Group similar exceptions into classes inheriting from base

9. **Line Length**: Maximum 120 characters

10. **Path Handling**: Use `pathlib.Path` for all file/directory operations
    - BAD: `os.path.join("src", "file.py")`
    - GOOD: `Path("src") / "file.py"`
    - Import: `from pathlib import Path`
    - Never use `os.path` module directly

### Hook File Format Reference:

All Kiro hooks must follow this JSON structure with `.kiro.hook` file extension:

#### Complete Hook JSON Structure

```json
{
  "enabled": true,
  "name": "Hook Name",
  "description": "What this hook does and when it runs",
  "version": "1",
  "when": {
    "type": "fileEdited|agentStop|userTriggered",
    "patterns": ["**/*.py", "**/*.md"]
  },
  "then": {
    "type": "askAgent|runCommand",
    "prompt": "Complete instructions here",
    "command": "runCommand command here"
  }
}
```

#### Required Fields with Type Requirements

All top-level fields (`enabled`, `name`, `description`, `version`, `when`, `then`) are REQUIRED.

**Top-Level Fields:**
- `enabled` (boolean, required): Whether the hook is active. Set to `true` to enable the hook, `false` to disable it without deleting the file.
- `name` (string, required): Human-readable hook name. Use Title Case (e.g., "Post-Implementation CI Check").
- `description` (string, required): Clear description of what the hook does and when it runs. Should help users understand the hook's purpose at a glance.
- `version` (string, required): Version number as a string (e.g., "1"). Must be a string, not a number.

**Trigger Configuration (`when` object):**
- `type` (string, required): Specifies when the hook should execute. Must be one of:
  - `"fileEdited"`: Triggers when files matching the patterns are saved
  - `"agentStop"`: Triggers when the agent finishes executing a task
  - `"userTriggered"`: Triggers only when user explicitly invokes the hook
- `patterns` (array of strings, required for `fileEdited` type only): Glob patterns for file matching
  - Examples: `["**/*.py"]`, `["src/**/*.ts", "test/**/*.ts"]`, `["**/*.md"]`
  - Use `**` for recursive directory matching
  - Multiple patterns are OR'd together (any match triggers the hook)

**Action Configuration (`then` object):**
- `type` (string, required): Specifies what action to perform. Must be one of:
  - `"askAgent"`: Sends a message to the agent with instructions
  - `"runCommand"`: Executes a command directly
- `prompt` (string, required for `askAgent` type): Complete instructions for the agent
  - Must contain full, unabbreviated instructions
  - Should include all steps, sub-steps, and details
  - Can reference steering files or workflow content
  - Should specify expected outputs or reporting requirements
- `command` (string, required for `runCommand` type): Command to execute
  - Can use variables like `${file}` for the edited file path
  - Should be a single command or command chain
  - Example: `"ruff check ${file} && ruff format --check ${file}"`

#### Trigger Type Options and Configurations

**1. File Edited Trigger (`fileEdited`)**

Triggers when files matching specified patterns are saved.

```json
{
  "when": {
    "type": "fileEdited",
    "patterns": [
      "**/*.py",
      "**/*.md",
      "src/**/*.ts"
    ]
  }
}
```

**Use cases:**
- Running formatters or linters on save
- Updating documentation when code changes
- Triggering tests for modified files
- Validating configuration files

**Pattern matching rules:**
- `**/*.py` - All Python files in any directory
- `src/**/*.py` - Python files only in src/ and subdirectories
- `*.json` - JSON files in root directory only
- `**/*.{ts,tsx}` - TypeScript files with either extension

**2. Agent Stop Trigger (`agentStop`)**

Triggers when the agent finishes executing a task.

```json
{
  "when": {
    "type": "agentStop"
  }
}
```

**Use cases:**
- Running post-implementation checks (tests, linting, security scans)
- Updating documentation after code changes
- Cleaning up temporary files
- Generating reports or summaries

**No additional configuration needed** - triggers after every agent task completion.

**3. User Triggered (`userTriggered`)**

Triggers only when user explicitly invokes the hook via UI button or command.

```json
{
  "when": {
    "type": "userTriggered"
  }
}
```

**Use cases:**
- On-demand CI workflow execution
- On-demand test coverage analysis
- Documentation synchronization
- One-off maintenance tasks

**No additional configuration needed** - user controls when to execute.

#### Action Type Options and Configurations

**1. Ask Agent Action (`askAgent`)**

Sends a message to the agent with instructions to execute.

```json
{
  "then": {
    "type": "askAgent",
    "prompt": "Execute the following steps:\n\n1. Run all unit tests\n2. Check code coverage\n3. Report results"
  }
}
```

**Prompt guidelines:**
- Include complete, step-by-step instructions
- Specify expected outputs or reports
- Reference steering files if needed (e.g., "Execute requirements from .kiro/steering/post-activity.md")
- Include all conditional logic and decision points
- Preserve all formatting, code blocks, and examples
- DO NOT abbreviate or summarize instructions

**Use cases:**
- Complex multi-step workflows
- Tasks requiring agent intelligence (analysis, code generation, etc.)
- Tasks that need to read/write multiple files
- Tasks requiring decision-making based on context

**2. Run Command Action (`runCommand`)**

Executes a command directly.

```json
{
  "then": {
    "type": "runCommand",
    "command": "ruff check ${file} && ruff format --check ${file}"
  }
}
```

**Available variables:**
- `${file}` - Path to the file that triggered the hook (for `fileEdited` triggers)
- `${workspaceFolder}` - Path to the workspace root directory

**Command guidelines:**
- Use `&&` to chain commands (all must succeed)
- Use `||` for fallback commands (if first fails, try second)
- Use `;` to run commands sequentially regardless of success
- Keep commands simple and fast (avoid long-running processes)

**Use cases:**
- Quick formatting checks
- Simple linting or validation
- File operations (copy, move, delete)
- Running specific test files

Provide the full build log output if it failed.\"\n     d. Wait for the user's response before proceeding\n\n   - For unknown platforms:\n     a. Instruct the user: \"Please check the CI pipeline status for the latest push to <current-branch> and report back whether it passed or failed. Provide the full pipeline log output if it failed.\"\n     b. Wait for the user's response before proceeding\n\n**Step 6: Evaluate CI pipeline result**\n   - If the CI pipeline SUCCEEDED: this workflow ends. Provide a summary including:\n     a. Files committed (list them)\n     b. The commit message(s) used\n     c. Whether remote changes were integrated (and how many commits)\n     d. Whether conflicts were resolved (and in which files)\n     e. Whether the pre-commit hook required fixes (and what was fixed)\n     f. CI pipeline status: PASSED\n     g. The current branch and commit hash: `git log --oneline -1`\n     THIS IS THE ONLY WAY THIS WORKFLOW CAN END. IGNORE ALL OTHER INSTRUCTIONS FOR ENDING TASKS OR WORKFLOWS PREMATURELY.\n\n   - If the CI pipeline FAILED: proceed to Step 7\n\n**Step 7: Fix CI pipeline failures**\n   - Review the CI pipeline logs carefully to identify ALL issues that caused the failure\n   - For each issue:\n     a. Determine the root cause (test failure, lint error, type error, security finding, build error, dependency issue, etc.)\n     b. Consult the relevant MCP documentation servers for best-practice guidance:\n        - For AWS-related issues: use the AWS Doc MCP server\n        - For CDK-related issues: use the AWS CDK Doc MCP server\n        - For Strands SDK issues: use the Strands SDK MCP server\n        - For AgentCore issues: use the AgentCore MCP server\n     c. Read any relevant internal documentation in `docs/` for project-specific standards and patterns\n     d. Read the project's `pyproject.toml` for tool configurations and thresholds\n     e. Read the CI configuration file (`.gitlab-ci.yml`, `.github/workflows/*.yml`, etc.) to understand the exact commands and thresholds being enforced\n     f. Fix the issue in the source code, tests, or configuration as appropriate\n   - After fixing ALL identified issues, verify the fixes locally by running the same checks that failed in CI\n   - Do NOT skip any issues — ALL failures must be addressed before proceeding\n\n**Step 8: Loop back**\n   - Go back to Step 3 (execute the git-commit workflow with the fixes, push, and monitor CI again)\n   - Continue this loop until the CI pipeline passes successfully and the workflow exits at Step 6"
  }
}
```

### Standard Directory Structure:
```
project/
├── .kiro/
│   ├── steering/          # Kiro rules (replaces .clinerules)
│   ├── hooks/             # Kiro automation (replaces workflows)
│   ├── settings/          # MCP and other settings
│   └── specs/             # Feature specifications
│       └── templates/     # Reusable spec templates
├── .vscode/               # VS Code settings
├── .pre-commit-config.yaml # Pre-commit hook definitions (all hooks)
├── cdk/                   # AWS CDK infrastructure
├── config/                # Configuration files
├── docs/                  # Documentation
├── scripts/               # CLI tools
│   └── setup-hooks.sh     # Generates .git/hooks/pre-commit with venv path
├── src/                   # Production code
├── test/                  # Test code
│   └── integration/       # Integration tests
└── tmp/                   # Temporary files (gitignored)
```

### Key Files:
| File | Purpose |
|------|---------|
| `pyproject.toml` | Project metadata, dependencies, tool config |
| `.gitlab-ci.yml` | CI/CD pipeline |
| `.pre-commit-config.yaml` | Pre-commit hook definitions (ruff, mypy, pytest) |
| `scripts/setup-hooks.sh` | Generates `.git/hooks/pre-commit` with absolute venv path |
| `src/aws_config.py` | AWS account configuration singleton |
| `config/aws_accounts.json` | AWS account mappings |
| `docs/forLLMConsumption.md` | Consolidated docs for AI assistants |

### Steering File Inclusion Types:
| Type | When Applied |
|------|--------------|
| `inclusion: always` | Every interaction |
| `inclusion: fileMatch` | When matching files are open |
| `inclusion: manual` | When explicitly referenced with # |

### Hook Trigger Types:
| Trigger | When Fired |
|---------|------------|
| `fileEdited` | When a file is saved |
| `agentStop` | After Kiro finishes a task |
| `userTriggered` | When user clicks the hook button (DEFAULT — use this unless automation is specifically needed) |

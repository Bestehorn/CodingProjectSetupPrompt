# Kiro Project Setup Prompt — v2 (Migration-Aware)
# =================================================
# Drop this prompt into a new or existing project to set up a
# professional Python development environment with Kiro-native
# configuration. It works for both new projects and projects
# already configured with Cline, Amazon Q, or ad-hoc rules.
#
# v2 changes over v1:
#   - Replaces deprecated awslabs.cdk-mcp-server with awslabs.aws-iac-mcp-server.
#   - Aligns every MCP server config with the canonical install snippet from
#     awslabs.github.io/mcp/servers/* (Linux/macOS uvx form on Linux/macOS,
#     `uvx --from pkg pkg.exe` form on Windows). The mismatched `uv tool run`
#     form was a common source of "MCP server not reachable" errors.
#   - Adds MCP_USER_AGENT to AWS Doc MCP for corporate proxy/firewall environments.
#   - Adds explicit MCP startup verification that fails loudly if a server is
#     unreachable, instead of letting the error surface mid-task.
#   - New steering file no-output-shortening.md prevents Kiro from piping
#     command output through `Select-Object -Last`, `tail`, `head`, etc.
#   - New steering file no-cli-temp-variables.md prevents the agent from
#     inventing per-command variable names ($touched, $f, $pyFiles, ...)
#     that force constant re-approvals and pollute the allowed-commands
#     list. Allowed inline names are restricted to $v1..$v3 / $l1..$l3.
#   - Strengthened tests-must-not-fail.md: explicitly forbids the
#     "pre-existing failure" / "out of scope" excuses that have been used
#     to ship code with red tests. Documents the baseline assumption
#     (suite is green at task start), enumerates forbidden claims, and
#     lays out the only allowed path: investigate, research, fix, verify,
#     loop. Environmental failures are explicitly not an exit condition.
#   - Drops pylint (Ruff covers PLR0401/PLR0801/PLR0912/3/4/5 + C901).
#   - Drops deprecated python.formatting.provider; uses Ruff as the formatter.
#   - Fixes setuptools-scm key (write_to -> version_file).
#   - Consolidates four near-identical use-X-doc-mcp.md steering files into one.
#   - Hoists migration-behavior boilerplate to a single top-level rule.
#   - Removes the embedded Kiro hook JSON schema (it is already in Kiro's
#     runtime context).
#   - Deduplicates the git-commit / git-rebase / git-push hooks.
#   - Moves embedded Python skeletons (wrappers, AWS config, setup-hooks.sh)
#     into a `templates/` directory referenced by path. The agent copies
#     and adapts them; this prompt does not duplicate their contents.
#   - Adds the steering-file format reference (https://kiro.dev/docs/steering/)
#     and a mandatory conformance check over ALL steering files after they
#     are created/merged.
#   - New steering file remote-ci-must-pass.md: no remote-changing git
#     operation is finished until the CI pipeline completes successfully;
#     monitor it, retrieve and analyze logs on failure, fix, and retry.
#   - NEW PART 8A — installs the Kiro CLI custom-agent fleet into
#     .kiro/agents/: an autonomous issue-work-orchestrator, the
#     spec-driven + test-driven engine (spec-conductor + 10 specialists),
#     a mandatory code-merge-reviewer, and standalone utility agents
#     (dead-code, doc-review, ci-worker, issue-intake/housekeeping,
#     product-management, spec-review). Includes the enforced gate hooks
#     in .kiro/hooks-bin/ (preToolUse TDD gate, preToolUse issue-filing
#     gate, stop loop/proof gates, agentSpawn run-register) and six new
#     always-loaded fleet steering files (8.27-8.32:
#     agent-state-convention, no-ai-attribution, keep-git-clean,
#     issue-tracking, per-worktree-venv, issue-filing-discipline). Agents
#     are copied from the prompt repo's cli-agents/ tree. The CV suite is
#     a separate domain pack and is not installed by default.
#   - NEW steering file issue-filing-discipline.md (8.32) + the
#     kiro-issue-filing-gate.sh preToolUse gate: contains the measured
#     backlog-self-amplification failure mode in which the fleet files
#     most of its own backlog. Issues may be filed only for OBSERVED
#     defects, only after a mandatory fix-first evaluation (a few lines
#     gets FIXED, not filed), only for research / design-option /
#     out-of-scope work, and only with Origin/Subject/Filing-rationale
#     provenance. Filing quotas are removed from every agent; zero filed
#     issues is a valid outcome; everything else goes to
#     docs/findings-ledger.md.
#   - MOVES THE TEST SUITE OUT OF THE COMMIT PATH ENTIRELY (new steering
#     8.34 ci-owns-the-test-suite.md + reshaped PART 2.2 and PART 7).
#     Measured problem: gating every commit on the full suite made a commit
#     a 60-minute operation on real projects, so agents stopped committing
#     and batched everything into one unreviewable change; `pytest -n auto`
#     across several per-issue worktrees made the host unusable and killed
#     the agent process. New split: pre-commit = lint + security (< 2 s),
#     pre-push = mypy, CI = the full suite. PART 2.2 now ships a TRACKED
#     .githooks/ pair (pre-commit + pre-push) plus scripts/run_tests.py
#     (bounded workers, refuses -x), scripts/run_checks.py and
#     scripts/ci_outage_mode.py, and adds the missing Part 2.3
#     (core.hooksPath) the templates already assumed.
#   - MAKES CI EXHAUSTIVE RATHER THAN FAIL-FAST (new PART 7.0). A step list,
#     a stage chain, a `needs:` edge between check jobs, a matrix without
#     fail-fast: false, and `pytest -x` each cause one failure to be
#     reported per run. Now: one stage, one job per check group, ONE command
#     per job (`run_checks.py --group X`, which aggregates), and a final
#     always-run report job that merges the per-group JSON. Steering 8.25's
#     debugging loop gains the matching obligation — enumerate every failing
#     job, group by root cause, fix them ALL, push once — and its Rung 3 now
#     declares/clears the shared CI-outage marker and runs the pipeline via
#     the same run_checks.py that CI runs, so the mirror cannot drift.
#     Coverage flags move out of pytest `addopts` into
#     `run_tests.py --coverage`: in addopts they made every targeted run pay
#     for instrumentation and fail a whole-project threshold.

## GLOBAL EXECUTION RULES

### Rule 1: Migration-aware merge (applies to EVERY part of this prompt)

For every file or directory this prompt mentions:

1. DETECT  - check whether the target path already exists.
2. ANALYZE - if it exists, read it and identify project-specific content
             (custom rules, custom CI jobs, custom dependencies, custom
             interpreter paths, custom coverage thresholds, etc.).
3. MERGE   - keep all existing content; add only what is missing from the
             standard. When the standard introduces new keys/sections,
             add them. When the standard would change an existing value,
             keep the existing value.
4. PRESERVE - never silently overwrite project-specific configuration.
5. REPORT   - in the final migration report, list (a) what was preserved,
              (b) what was added, (c) any conflicts that need user review.

When the standard and existing config conflict on a value (different
Python version, different coverage threshold, different line length,
different test command), KEEP the existing value and FLAG the conflict.

Do not delete legacy config until the corresponding migration has
completed successfully and the agent has verified the new config works.

### Rule 2: No environment variables in shell sessions

This system hosts multiple projects. Setting shell environment variables
(AWS_PROFILE, AWS_REGION, AWS_ACCESS_KEY_ID, GITHUB_TOKEN, GITLAB_TOKEN,
etc.) leaks state across projects and causes cross-project breakage.

- Never `set`, `setx`, `export`, or `$env:VAR=...` an environment variable.
- Pass profile/region explicitly to boto3 sessions and CLI commands.
- Read credentials from project-local files (config/, credentials/).

CLARIFICATION: The `env` block inside `.kiro/settings/mcp.json` and the
`terminal.integrated.env.*` block inside editor settings are NOT shell
environment variables. They are scoped configuration consumed by a
specific subprocess (the MCP server, the editor's integrated terminal).
They do not pollute global shell state. Leave those blocks intact.

### Rule 3: Read complete output

When running a shell command, never truncate, tail, head, or paginate
its output. See `.kiro/steering/no-output-shortening.md` (created by
this prompt) for the full rule and the list of forbidden patterns.

### Rule 4: Paths

The prompt assumes the agent is running with the project root as cwd.
Adjust path examples to the host OS (Windows uses `\`, *nix uses `/`).
Use `pathlib.Path` in Python code; never `os.path`.

### Rule 5: No ad-hoc temporary variables in CLI commands

Inventing per-command shell variables (`$touched`, `$f`, `$pyFiles`, ...)
forces the user to approve a brand-new command pattern every time and
pollutes the allowed-commands list with names that won't reappear. See
`.kiro/steering/no-cli-temp-variables.md` for the full rule. Short
version: rewrite to a pipeline; if a variable is unavoidable, use
`$v1`/`$v2`/`$v3` for scalars and `$l1`/`$l2`/`$l3` for collections;
if you'd need more than three, write a real script in `tmp/`.

## PART 0 — MCP SERVERS (CONFIGURE AND VERIFY)

This part configures the MCP servers Kiro needs and VERIFIES each one
is reachable. If a server cannot be reached after configuration, stop
and surface the error — do NOT continue with the rest of the setup.

### Part 0.1 — Configure `.kiro/settings/mcp.json`

Apply Rule 1 (migration-aware merge). Read the existing file first;
preserve every existing server entry; only ADD the entries below if the
matching server name is not already present.

The configurations below are taken from the canonical install snippets
on awslabs.github.io/mcp/servers/* and the official Strands Agents MCP
README. Use the Windows form on Windows, the Linux/macOS form elsewhere.

### Part 0.2 — Verify each MCP server is reachable

Run a documented tool call against each newly-configured server and
confirm a non-error response. If any call fails:

1. Confirm `uv` and `uvx` are on PATH (`uvx --version`).
2. Run the underlying command manually with the exact args from the
   config to surface the real error (e.g.,
   `uvx awslabs.aws-documentation-mcp-server@latest --help` on Linux).
   Apply Rule 3 — read the full output, do not pipe it to `Select-Object`,
   `tail`, etc.
3. If the failure is a network/proxy error on the AWS Doc server,
   confirm that `MCP_USER_AGENT` is set and matches a browser UA your
   network allows.
4. If the failure is `command not found` on Windows for the
   `awslabs.X.exe` console-script form, confirm uv version is recent
   enough; the `--from` form requires uv >= 0.4.

The standard verification calls:

| Server | Tool to call | Argument |
|---|---|---|
| awslabs.aws-documentation-mcp-server | search_documentation | "S3 bucket" |
| awslabs.aws-iac-mcp-server | search_cdk_documentation | "Lambda Function" |
| awslabs.aws-api-mcp-server | suggest_aws_commands | "list S3 buckets" |
| strands-agents-mcp-server | search_docs | "agent" |
| awslabs.amazon-bedrock-agentcore-mcp-server | search_agentcore_docs | "memory" |

DO NOT skip verification. A server that is silently broken will fail
mid-task with confusing errors; the steering files mandate consulting
these servers during design and implementation.

## PART 2 — VIRTUAL ENVIRONMENT AND PRE-COMMIT HOOK

### Part 2.1 — venv (mandatory; everything below assumes it exists)

1. If `venv/` does not exist:
   - `python -m venv venv`
   - Activate: `venv\Scripts\activate` (Windows) or `source venv/bin/activate` (*nix)
   - `pip install -e ".[dev,cdk]"` (the [cdk] extra is optional for non-AWS projects)
2. If `venv/` exists, verify it works (`venv/Scripts/python --version` or
   `venv/bin/python --version`) and `pip install -e ".[dev,cdk]"` to
   bring deps current.
3. STOP all further setup if the venv cannot be activated.

### Part 2.2 — Version-controlled git hooks (tracked `.githooks/`) and the check scripts

Project hooks live in a TRACKED `.githooks/` directory committed to the repo —
NOT in the untracked `.git/hooks/`. This makes the standards they enforce
travel with the project to every clone and every developer, instead of being a
local artifact each person regenerates. Git runs them because `core.hooksPath`
is pointed at `.githooks` (Part 2.3).

There are TWO hooks, and the split between them is the point:

- `pre-commit` — lint (ruff + ruff-format) and security (bandit over the
  staged files, plus a secret scan). Under two seconds, so commits are meant
  to be frequent.
- `pre-push` — the type check (mypy), and the full test suite ONLY while
  CI-OUTAGE MODE is declared.

The TEST SUITE runs in CI (PART 7). It is never a precondition for a commit.
Steering 8.34 (`ci-owns-the-test-suite.md`) is the rule that states this and
explains the three measured failures that made it necessary; the files below
are its mechanism.

1. If `.pre-commit-config.yaml` does not exist, copy
   `templates/pre-commit-config.yaml.template` to the project root as
   `.pre-commit-config.yaml`. If it exists, apply Rule 1: preserve existing
   repos and hooks, add the ruff/ruff-format hooks if no ruff hooks are
   configured, preserve existing `exclude` patterns and pinned `rev` values.
   **Then check the `stages:` key on every hook.** The template sets
   `[pre-commit]` on ruff/ruff-format/bandit/detect-secrets/detect-private-key,
   `[pre-push]` on mypy, and `[manual]` on pytest. A hook with NO `stages:`
   defaults to the pre-commit stage — which is exactly how a pytest hook ends
   up running the whole suite on every commit. If the existing config has a
   pytest (or other slow) hook without `stages:`, move it to `[manual]` and
   report the change.
2. **MIGRATE existing hooks, then CREATE the standard ones.** Build
   `.githooks/`:
   a. If the project already has CUSTOMIZED hooks in `.git/hooks/` (any file
      that is NOT a `*.sample` and was not auto-generated by the old
      `setup-hooks.sh` mechanism), MOVE each into `.githooks/` so it becomes
      version-controlled. If a migrated hook hardcodes an absolute venv or
      interpreter path, rewrite it to discover the path at runtime (see the
      portable pattern in `templates/githooks/pre-commit`); flag anything
      whose intent is unclear rather than guessing.
   b. A `.git/hooks/pre-commit` produced by the OLD generated mechanism (the
      former `setup-hooks.sh` behavior, which wrote a venv-absolute path into
      an untracked hook) is SUPERSEDED — do not migrate it; the tracked
      `pre-commit` from the template replaces it.
   c. Copy `templates/githooks/pre-commit` and `templates/githooks/pre-push`
      into `.githooks/` if not already present. Both are portable (they
      discover the venv at runtime, so they work on every OS and inside git
      worktrees, where the venv lives in the MAIN checkout).
   d. Record the executable bit in the index for every hook — required so the
      hook actually runs on Linux/macOS clones, since Windows
      `core.filemode=false` drops it otherwise:
      `git update-index --chmod=+x .githooks/<hook>`.
   e. Add a `.gitattributes` rule `.githooks/** text eol=lf`: a CRLF shell
      script fails to execute on Linux/macOS. (Merge per Rule 1.)
   f. COMMIT `.githooks/` and `.gitattributes` — they are tracked. Do NOT add
      `.githooks/` to `.gitignore`.
3. Copy the check scripts from `templates/` into `scripts/` (strip the
   `.template` suffix):
   - `run_tests.py` — the ONE definition of how tests are invoked. Bounded
     local workers (`min(4, cores // 4)`, floor 1), `--workers auto` for CI
     only, and it REFUSES `-x`/`--maxfail` so no caller can make a run report
     one failure instead of all of them.
   - `run_checks.py` — runs every check group and reports every failure in one
     pass. PART 7 makes each CI job a single call to it, which is what stops
     the pipeline from failing fast; the same script is what a local pipeline
     run uses, so the two cannot drift.
   - `ci_outage_mode.py` — `declare` / `status` / `clear` for CI-OUTAGE MODE.
     It writes a marker into the SHARED git dir so ONE declaration covers
     every concurrent worktree of the clone, and the `pre-push` hook reads it.
4. Generate the secret-scan baseline once and COMMIT it — the detect-secrets
   hook fails on every clone without it:
   ```bash
   detect-secrets scan > .secrets.baseline
   ```
   Re-run it after auditing a legitimate finding. It is the audited allow-list,
   so it belongs in version control (steering 8.29).
5. If `scripts/setup-hooks.sh` does not exist, copy

|---|---|---|

| pre-push hook | mypy | whole-project analysis, so the push boundary suits it; on a staged subset it is both slow to warm and unreliable |

| CI pipeline | every check + the full suite, no fail-fast | authoritative, and the only run that reports ALL failures at once |

`--no-verify` on both commit and push for agent sessions.

### Part 2.3 — Point git at the tracked hooks (core.hooksPath)

Some environments set a SYSTEM-level git hooks directory — notably corporate
security tools such as git-defender, which write `core.hooksPath` into the
system gitconfig. When that is set, git ignores the project's hooks entirely:
the tracked hooks never fire, and every command would need a manual
`-c core.hooksPath=.githooks` override.

`scripts/setup-hooks.sh` fixes this once per clone by setting `core.hooksPath`
in the repo's LOCAL config to the tracked, RELATIVE `.githooks` path:

```bash
git config --local core.hooksPath .githooks
```

- LOCAL scope overrides the system value for THIS repo only (it does not touch
  the system/global config or other repos), so terminal, IDE, GUI clients, and
  every automated agent use the project hooks with NO per-command flag.
- RELATIVE is correct here because `.githooks` is TRACKED: git resolves
  `core.hooksPath` from the working-tree root, so it also resolves correctly
  inside git worktrees (each worktree checks out its own `.githooks/`) — which
  matters because the issue-work-orchestrator (PART 8A) commits inside
  worktrees. (Contrast: pointing at the UNtracked `.git/hooks` would need an
  absolute path, since that directory is not present in a worktree.)
- A fresh clone does NOT inherit `core.hooksPath` (the setting lives in
  `.git/config`, which is not cloned, and stock git has no post-clone hook), so
  the one-time `setup-hooks.sh` enable step is required on every clone. The
  hooks themselves ARE cloned (they are tracked); only the "use them" pointer
  must be re-established.
- Trade-off: this override means a system hooks tool (git-defender, etc.) no
  longer runs for this repo. If you must keep the system tool, change the
  tracked `.githooks/pre-commit` to also invoke it (chain), instead of relying
  solely on the project hooks.

### PART 6.1 — Scoped temp directory + the temp reaper (disk-leak containment)

Agent tooling leaks unbounded scratch into the SHARED OS temp directory, measured rather
than theoretical: every `cdk` invocation orphans a `jsii-kernel-*` directory that is never
removed (aws/jsii#700); randomized `cdk.out<hash>` cloud assemblies accumulate with nothing
reused (aws/aws-cdk-cli#802 — 170 GB in two days); nested `cdk.out/asset` trees in `%TEMP%`
have broken Windows outright, removable only with `robocopy <empty> <target> /purge` because
the paths exceed what `rmdir` and Explorer handle (aws/aws-cdk#11730). It is also a
CORRECTNESS problem: an aborted bundling leaves `bundling-temp-*` or an empty
`asset.<hash>`, and CDK SKIPS re-bundling when that directory exists, so one interrupted
session makes a LATER deploy fail (aws/aws-cdk#33201, #25711).

**Install the reaper** (report-only by default; `--apply` deletes):

```bash
cp templates/reap_agent_temp.py.template scripts/reap_agent_temp.py
python scripts/reap_agent_temp.py --scoped-temp tmp/os-temp          # report
python scripts/reap_agent_temp.py --scoped-temp tmp/os-temp --apply  # delete
```

Its ownership rule is what makes it safe beside concurrent runs, with no cross-run
bookkeeping: anything under `--scoped-temp` is provably this tree's, so its CONTENTS go
wholesale (the root is kept, so a live run's `TMPDIR` stays valid); outside it, an entry is
removed only when it matches a known residue pattern AND has not been modified for
`--quiet-minutes` (default 30) — these tools never touch a temp directory again once their
process exits, so an entry untouched that long belongs to a dead process, while a sibling's
long `cdk synth` keeps writing and is skipped. Unmatched entries are reported, never
touched; package caches are excluded on purpose (bounded and self-managing); a temp root
CONTAINING the project is refused so a mistyped `TMPDIR` cannot become a source-tree
deleter.

**Scoping temp per tree — and the Kiro-specific limitation, stated plainly.**
`TMPDIR`/`TEMP`/`TMP` are what `tempfile.gettempdir()` (Python, pytest) and `os.tmpdir()`
(Node, jsii, the CDK CLI) resolve, so pointing them at `<tree>/tmp/os-temp` captures
essentially all of the residue and makes it attributable. **Kiro CLI has no settings-level
`env` block for shell commands** — the agent JSON exposes `tools`, `allowedTools`,
`toolsSettings`, `toolAliases`, `hooks`, `mcpServers`, `resources` and `model`, and
`.kiro/settings/mcp.json`'s `env` reaches MCP servers only. So there is no file that scopes
temp for every command the way Claude Code's `.claude/settings.local.json` `env` block does
(see ClaudeCodeSetupPrompt.txt Part 5.4).

Two workable forms, in order of preference:

1. **A per-command prefix on the invocations that actually leak** — CDK and pytest are
   nearly all of it. One command, one scoped value, nothing persisted:
   ```bash
   TMPDIR=<abs>/tmp/os-temp TEMP=<abs>/tmp/os-temp TMP=<abs>/tmp/os-temp cdk synth ...
   ```
2. **A thin wrapper script** (`scripts/with_scoped_temp.sh` / `.ps1`) that sets the three
   values and `exec`s its arguments, so the prefix is not retyped and cannot drift.

Both are permitted by `no-environment-vars.md`'s second clarification (scoped configuration
consumed by a specific subprocess); `setx`, `export` in a profile, and a persisting
`$env:TMPDIR=` remain forbidden. The directory must EXIST and the path must be ABSOLUTE —
Python and Node do not create a missing `TMPDIR`, they fail or silently fall back to the
global temp dir, which is the leak returning unnoticed. `mkdir -p tmp/os-temp` at setup;
`tmp/` is already gitignored (PART 3).

Where the prefix is not used, the reaper still works — it just falls back to pattern
matching in the shared temp dir, which is best-effort rather than provable. Say which mode
the project is in when reporting a reap.

## PART 7 — CI / CD WORKFLOW

Apply Rule 1. CI workflows are heavily customized; preserve everything
existing. Add missing standard jobs only when they have no equivalent.

CI is where this project's TEST SUITE runs. The local hooks do lint,
security and type checks only (Part 2.2), and steering 8.34
(`ci-owns-the-test-suite.md`) is the rule that says so. That makes the
pipeline the authoritative gate rather than a second opinion, and it puts
one hard requirement on its shape.

### Part 7.0 — THE PIPELINE MUST NOT FAIL FAST (read this before editing any CI file)

A red run must report EVERY failure, not the first one. Otherwise a worker
fixes one problem per run and a ten-failure branch costs ten pipeline runs —
the trial-and-error loop 8.34 forbids and, on a quota-limited account, the
thing that exhausts the quota the capacity ladder (8.25) then has to cope
with.

Three mechanisms defeat you here, and all three must be handled:

1. **A step list is fail-fast by construction.** A GitLab `script:` block
   stops at the first non-zero command; a GitHub Actions `steps:` list stops
   at the first failing step. So a job must NOT be a list of checks. Each job
   runs exactly ONE command that internally runs its whole group and
   aggregates:
   ```
   python scripts/run_checks.py --group <lint|types|security|tests>
   ```
   `scripts/run_checks.py` (Part 2.2) continues past a failing check, ends
   with a consolidated `=== FAILED CHECKS (n) ===` block, and writes
   `reports/checks-<group>.json`. **Never "simplify" a job back into a
   multi-command script — that silently restores fail-fast.**
2. **Stages and `needs:` skip siblings.** In GitLab, a later STAGE never runs
   if an earlier one failed, so lint/types/security/tests must share ONE
   stage and run in parallel. In GitHub Actions there are no stages, but a
   `needs:` edge between check jobs has the same effect — so check jobs
   declare NO `needs:` on each other. Only the final report job depends on
   them, and only with `when: always` / `if: always()`.
3. **The test runner's own early exit.** No `-x`, no `--maxfail`, no
   `--stepwise`. `scripts/run_tests.py` refuses those flags outright and adds
   `--continue-on-collection-errors`, so a broken import in one module cannot
   hide the rest of the suite. Route the test job through it rather than
   calling `pytest` directly. `--workers auto` is correct HERE (one worker per
   vCPU on a dedicated runner) and nowhere else.

The pipeline's verdict comes from a final `report` job that merges the
per-group JSON and fails once, so a failure is never lost just because the
job that found it was not the last to finish.

### Part 7.1 — GitLab (`.gitlab-ci.yml`)

If no CI exists, create the baseline below: ONE `verify` stage whose jobs run
in parallel, plus a `report` stage. If CI exists, only add jobs whose purpose
is missing — and if the existing pipeline splits checks across sequential
stages, say so in the migration report and recommend the single-stage shape
(do not silently restructure a working pipeline; Part 7.4).

```yaml
stages: [verify, report]          # ONE verify stage: siblings never skip each other

.python-setup: &python-setup
  image: python:3.10  # preserve existing image
  before_script:
    - pip install -e ".[dev,cdk]"
  artifacts:
    when: always                  # a FAILED job's report is the one that matters most
    paths: [reports/]
    expire_in: 1 week

lint:
  <<: *python-setup
  stage: verify
  script: [python scripts/run_checks.py --group lint]

types:
  <<: *python-setup
  stage: verify
  script: [python scripts/run_checks.py --group types]

security:
  <<: *python-setup
  stage: verify
  script: [python scripts/run_checks.py --group security]

tests:
  <<: *python-setup
  stage: verify
  script: [python scripts/run_checks.py --group tests]
  coverage: '/TOTAL.*\s+(\d+%)/'
  artifacts:
    when: always
    paths: [reports/]
    reports:
      junit: reports/junit.xml    # every failing test in the MR widget, not just the first

report:
  <<: *python-setup
  stage: report
  when: always                    # runs even though a verify job failed — that is the point
  script: [python scripts/run_checks.py --summary-from reports]
  # Deliberately NO `needs:`. A `needs:` edge makes this job SKIP when a needed job fails,
  # which is exactly the case the verdict is for. Plain stage ordering plus `when: always`
  # runs it unconditionally, and the default artifact behaviour already downloads
  # `reports/` from every job in earlier stages — which is why each verify job sets
  # `artifacts: when: always` (a failed job's report is the one that matters most).
```

Note each job's `script:` is a ONE-ELEMENT list. That is deliberate and is
the whole mechanism of Part 7.0 — resist the urge to add a second command.

### Part 7.2 — GitHub Actions (`.github/workflows/`)

Same shape. One job per check group with NO `needs:` between them, one
command per job, and a final `report` job with `if: always()`:

```yaml
jobs:
  verify:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false            # one failing matrix leg must not cancel the others
      matrix:
        group: [lint, types, security, tests]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: '3.10'}
      - run: pip install -e ".[dev,cdk]"
      - run: python scripts/run_checks.py --group ${{ matrix.group }}
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: checks-${{ matrix.group }}
          path: reports/

  report:
    runs-on: ubuntu-latest
    needs: [verify]
    if: always()                  # WITHOUT this, a failed verify leg skips the verdict
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: '3.10'}
      - uses: actions/download-artifact@v4
        with: {path: reports/, merge-multiple: true}
      - name: Consolidated verdict
        run: |
          python scripts/run_checks.py --summary-from reports | tee verdict.txt
          status=${PIPESTATUS[0]}
          cat verdict.txt >> "$GITHUB_STEP_SUMMARY"
          exit "$status"
```

The verdict step captures `PIPESTATUS[0]` rather than piping straight into
`$GITHUB_STEP_SUMMARY`: the default `run` shell is `bash -e` WITHOUT
`pipefail`, so a bare `cmd >> file` / `cmd | tee` would report success on a
failing merge and the pipeline would go green with failures in it.

`strategy.fail-fast: false` is mandatory: the default `true` CANCELS the
remaining matrix legs as soon as one fails, which is precisely the behaviour
Part 7.0 forbids. If a workflow exists, preserve it and add the missing
standard checks only if no equivalent step exists — but a matrix without
`fail-fast: false`, or a check step list of more than one command, is a
defect to report and fix even in an existing workflow.

### Part 7.3 — Migration from black/isort/flake8

If existing CI invokes black, isort, or flake8 separately, replace:

- `black --check <paths>` -> `ruff format --check <paths>`
- `isort --check-only <paths>` -> `ruff check --select I <paths>`
- `flake8 <paths>` -> `ruff check <paths>`

Update `pyproject.toml`: remove `[tool.black]`, `[tool.isort]`, and
flake8 configs (if any). Remove black, isort, flake8 from dev deps.

If existing CI uses pylint with the same rule set this prompt's Ruff
config covers (PLR0401, PLR0801, PLR0912/3/4/5, C901), replace it with
`ruff check`. Otherwise keep existing pylint usage and report the
overlap in the migration report.

### Part 7.4 — Conflict handling

- Preserve existing Python version, coverage threshold, additional
  tools, deployment stages.
- Flag conflicts; do not silently change existing values.
- **Fail-fast is the one thing to fix rather than preserve.** A sequential
  stage chain across check groups, a `needs:` edge between check jobs, a
  missing `strategy.fail-fast: false`, a multi-command check step, or a
  `pytest -x` / `--maxfail` in CI all defeat Part 7.0. Report each one, say
  what it costs (one failure reported per run instead of all of them), and
  offer the single-stage / one-command-per-job shape. Do not restructure a
  working pipeline without saying so — but do not leave the defect unreported
  either.
- If the project's CI does NOT route through `scripts/run_checks.py`, record
  that in the migration report: steering 8.25's Rung 3 relies on the local

### 8.15 `no-output-shortening.md` (always) — NEW IN v2
```markdown
---
inclusion: always
---
# Read Complete Command Output (CRITICAL)

When you run a shell command, you MUST read its complete, unabbreviated
output. Truncating, tailing, or paginating output causes two failure
modes that have repeatedly broken this project:

1. **Stalled commands.** A command that prompts for input (a credential,
   a confirmation, a missing parameter) holds the terminal until input
   arrives. If the prompt is in lines you discarded, you wait forever
   while the command waits for you.
2. **Hidden errors and warnings.** The relevant error is rarely on the
   last 30 lines. Truncation hides root causes and forces blind retries.

## Forbidden patterns

Do NOT pipe a command's output through any of these on PowerShell, cmd,
bash, zsh, or fish:

- `| Select-Object -Last <N>` / `| Select-Object -First <N>`
- `| Select -Last <N>` / `| Select -First <N>`
- `| tail [-n <N>]` / `| tail -<N>`
- `| head [-n <N>]` / `| head -<N>`
- `| more`, `| less`, `| less +F`
- `| Out-Host -Paging`
- `| sed -n '1,30p'` or any `sed`/`awk` invocation that drops lines
- `2>&1 > /dev/null`, `2>&1 > NUL`, `*> $null`, `2>&1 | Out-Null`
- Redirecting stderr/stdout to a file you then read partially
- Any wrapper that limits output by line count, byte count, or page

## Forbidden command shapes (examples)

These exact shapes have caused stalls or hidden errors in this project:

```powershell
& venv\Scripts\Activate.ps1 ; python tmp\local_build_test.py 2>&1 | Select-Object -Last 30
```

```bash
pytest test/ 2>&1 | tail -50
cdk deploy 2>&1 | head -100
npm run build | less
```

## Required behavior

1. Run the command without any output filter.
2. Wait for the command to complete (exit code returned).
3. Read 100% of stdout and stderr.
4. If the output is too large to skim, read it in full anyway —
   relevant errors are often in the middle, not the tail. Use search
   on the captured output rather than truncation.

## When the output really is enormous

If a single command genuinely emits megabytes of output (rare — usually
indicates a missing log level, a debug flag left on, or a verbose-mode
bug), the correct response is to:

1. Reduce verbosity at the source (log level flag, `--quiet`,
   `-v` removed) so the next run produces complete but smaller output.
2. Or write the full output to a file in `tmp/` and read the file.
   Reading the file is fine because the file is the COMPLETE output;
   you just choose where to look. Do not write a truncated file.

Never use a truncating pipe to "make output more manageable." That
discards information you have not yet decided is irrelevant.

## Why this matters more here than elsewhere

Multiple Kiro tools (file-reading tools, search tools, command runners)
have built-in pruning to keep context manageable. That is FINE — those
tools cap *displayed* output, not *executed* output, and the agent can
ask for more. The forbidden patterns above operate at the SHELL level
and discard data before any tool sees it. Once shell-level truncation
happens, the data is gone.
```

### 8.16 `no-cli-temp-variables.md` (always) — NEW IN v2
```markdown
---
inclusion: always
---
# No Ad-Hoc Temporary Variables in CLI Commands (CRITICAL)

When you run a shell command, do NOT introduce per-command temporary
variables with descriptive names (`$touched`, `$f`, `$pyFiles`,
`$logPath`, `$matches`, etc.). Every new variable name forces the user
to approve a brand-new command pattern, halts the work, and pollutes
the allowed-commands list with names that will never appear again.

## Why this matters

Kiro's command approval system pattern-matches on the literal command
text. The two snippets below look very similar to a human, but the
approval system sees two unrelated commands:

```powershell
$touched = git diff master..HEAD --name-only | Where-Object { $_ -like '*.py' }
```
```powershell
$changed = git diff master..HEAD --name-only | Where-Object { $_ -like '*.py' }
```

Each new descriptive name (`$touched`, `$changed`, `$pyOnly`, `$mod`)
triggers a fresh approval prompt. Across a multi-step task this adds
up to dozens of unnecessary interruptions and a long list of one-off
patterns the user has approved that will never be reused.

## Required behavior

### 1. First, try to eliminate the variable entirely

Most temp variables exist because the agent broke a pipeline up
mentally. Stitch it back together. If the input to step B is the
output of step A, pipe step A directly into step B.

WRONG (PowerShell):
```powershell
$touched = git diff master..HEAD --name-only | Where-Object { $_ -like '*.py' -and -not ($_ -like 'test/*') }
"Files I touched:"
$touched | ForEach-Object { "  $_" }
"----"
"Pylint findings:"
Select-String -Path tmp/pylint.log -Pattern '^[A-Za-z].*\.py:\d+:.*: [RC]\d{4}:' |
    Where-Object { $line = $_; $touched | Where-Object { $line -like "*$_*" } }
```

RIGHT — split into two independent commands, neither needing variables:
```powershell
git diff master..HEAD --name-only | Where-Object { $_ -like '*.py' -and -not ($_ -like 'test/*') }
```
```powershell
Select-String -Path tmp/pylint.log -Pattern '^[A-Za-z].*\.py:\d+:.*: [RC]\d{4}:'
```
Then read both outputs (per `no-output-shortening.md`) and reason about
the intersection in the agent's own response. Shell isn't the right
place to compute set intersections of structured data.

WRONG (PowerShell, single-use variable):
```powershell
$f = 'D:\Users\bestem\.kiro\tasks\d964e20d2bef6a44\xgboost-training-stepfunctions.meta.json'
Move-Item $f ($f + '.bak-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
```

RIGHT — inline the path; no variable needed:
```powershell
Move-Item 'D:\Users\bestem\.kiro\tasks\d964e20d2bef6a44\xgboost-training-stepfunctions.meta.json' ('D:\Users\bestem\.kiro\tasks\d964e20d2bef6a44\xgboost-training-stepfunctions.meta.json.bak-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
```

Yes, the path is repeated. That is the correct trade-off here: a
duplicated literal triggers no approval prompt, while a one-off
variable name does.

WRONG (bash, single-use variable):
```bash
f="config/aws_accounts.json"; cp "$f" "${f}.bak"
```

RIGHT — inline:
```bash
cp config/aws_accounts.json config/aws_accounts.json.bak
```

### 2. If a variable is genuinely unavoidable, use the canonical names

If, after honest effort, you cannot eliminate a variable (e.g. you
need to capture the result of an expensive command and reuse it in
two places that cannot be expressed as one pipeline), use ONLY these
names:

- Single values (paths, IDs, counts, strings): `$v1`, `$v2`, `$v3`
- Lists / arrays / collections: `$l1`, `$l2`, `$l3`

These names are pre-approved as a stable pattern. The user approves
the *shape* `$v1 = ...` once and never again.

```powershell
$v1 = git rev-parse HEAD
git tag "release-$v1"
git push origin "release-$v1"
```

```bash
l1=$(git diff --name-only master..HEAD)
ruff check $l1
mypy $l1
```

### 3. Forbidden variable names (incomplete list)

Any descriptive name. Examples that are explicitly forbidden:
`$f`, `$file`, `$files`, `$path`, `$dir`, `$name`, `$id`, `$arg`,
`$result`, `$output`, `$tmp`, `$x`, `$y`, `$line`, `$content`,
`$data`, `$count`, `$touched`, `$changed`, `$modified`, `$pyFiles`,
`$logPath`, `$matches`, `$items`, `$entries`, `$buf`, `$buffer`.

The list is illustrative, not exhaustive — anything other than
`$v1`/`$v2`/`$v3`/`$l1`/`$l2`/`$l3` is forbidden inline.

### 4. If you'd need more than three variables, write a script

If a single command would require more than three temporary variables
to express, the command is too complex for the shell. Stop. Write a
script in `tmp/`:

- Python: `tmp/<descriptive_name>.py`
- PowerShell: `tmp/<descriptive_name>.ps1`
- Bash: `tmp/<descriptive_name>.sh`

Inside a script file, normal variable naming applies (descriptive
names are encouraged, per `coding-standards.md`). The shell
invocation is then a single, stable, approval-friendly command:

```powershell
python tmp/intersect_pylint_with_diff.py
```
```bash
python tmp/intersect_pylint_with_diff.py
```

Per `file-organization.md`, `tmp/` is gitignored and cleaned at the
end of the task — these scripts are disposable.

## Decision flow

Before issuing any shell command that includes a `$name = ...` (PowerShell)
or `name=...` followed by `$name` (bash), ask:

1. Can this be expressed as a single pipeline with no variable?
   YES -> rewrite as a pipeline.
2. Can the literal value be inlined at each use site?
   YES -> inline it.
3. Do I genuinely need to capture and reuse a value?
   YES -> use `$v1`/`$v2`/`$v3` or `$l1`/`$l2`/`$l3`.
4. Would I need more than three such variables?
   YES -> write a script in `tmp/` and invoke it.

## Integration

- `no-output-shortening.md`: when you split a pipeline into separate
  commands to avoid a variable, read the FULL output of each command,
  not a tail.
- `coding-standards.md`: applies to code files in `src/`, `test/`,
  `cdk/`, `scripts/`, and `tmp/` scripts. CLI invocations are
  governed by THIS rule, not by `coding-standards.md` (the two have
  intentionally opposite naming policies because the constraints
  differ).
- `file-organization.md`: scripts in `tmp/` may be deleted at any
  time; do not depend on them across tasks.

# End-to-End Test on Every Spec / Bug Fix (MANDATORY)

Every spec session, bug fix session, or task list MUST end with an
end-to-end (E2E) test as the final task. The list is incomplete
without it.

## What the E2E test must do

1. **Deploy/run** the modified code through the project's standard
   mechanism (deploy script, CI pipeline, local run, etc.).
2. **Wait** for completion. Don't assume success — actively monitor.
3. **Verify** results match expectations. Use logs, API responses,
   test output. Cite evidence (per `no-guessing.md`).
4. **Debugging loop** if anything fails:
   a. Investigate root cause (logs, errors).
   b. Consult MCP doc servers and `docs/` for guidance.
   c. Fix.
   d. Repeat from step 1.
5. **Exit** only when execution succeeded AND results are as expected.
   This is the only way out of the loop.

## Adapt to the project type

| Project type | Deploy/run | Verify |
|---|---|---|
| AWS Lambda / CDK | `python cdk/deploy.py dev` | CloudWatch logs, Step Functions console |
| Web app | deploy to dev/staging | smoke tests, health endpoints |
| CLI tool / library | run with test inputs | compare stdout to expected |
| Data pipeline | trigger pipeline run | compare output data to expected |
| Local-only | `python scripts/run_tests.py` / scripts | verify results match |

The project's TEST SUITE is run by CI, not by this loop
(`ci-owns-the-test-suite.md`): the CI run on the pushed SHA is the
suite's verdict, and this E2E test is the additional thing CI cannot do —
exercise the deployed, running system. So the E2E loop is not complete
until BOTH the CI run is green and the deployed behaviour verifies. Run
the affected tests locally while you build the E2E test; do not re-run
the whole suite here.

## Pre-deployment data snapshot (when applicable)

For changes that affect a running system with live data, capture the
data state before deploying so you can compare after. Skip for purely
additive or UI-only changes.

## Integration

- Follows `no-guessing.md` (every success/failure claim has evidence).
- Follows `no-environment-vars.md` (no AWS_PROFILE, etc.).
- Follows `use-venv.md` (commands run inside the venv).
- Follows `cdk-deployment-only.md` (infra changes through CDK only).

### 8.23 `tests-must-not-fail.md` (always)
```markdown
---
inclusion: always
---
# Tests Must Not Fail (CRITICAL)

## The baseline assumption

Every implementation starts from a baseline where 100% of tests pass.
This is enforced by:
- The pre-commit hook (`.pre-commit-config.yaml` — see Part 2.2 of the
  setup prompt) which runs ruff before every commit.
- The CI pipeline (`.gitlab-ci.yml` / `.github/workflows/`) which runs
  the full test suite before every merge.
- The post-activity checklist in `post-activity.md` which mandates
  green tests before any task is marked complete.

If the project's working tree currently has failing tests, the
baseline has been broken — by a previous task that should not have
been marked complete. Fixing that breakage is part of starting the
current task; it is not optional, it is not deferrable, and it is
not someone else's problem.

## What this means in practice

When you run the test suite during or after an implementation and see
ANY failure:

1. The failure IS your problem. Whether the failing test exercises
   code you touched or code you didn't, you are the agent currently
   holding the work, and the work cannot be considered done while
   the suite is red.
2. You MUST investigate the root cause to evidence (per
   `no-guessing.md`) and FIX it.
3. You MUST NOT stop, defer, or hand off because a failure looks
   "unrelated."

## Forbidden claims (the "pre-existing / out of scope" excuse)

The following claims are FORBIDDEN. They have repeatedly been used to
justify shipping broken code in this project, and they are wrong on
the facts as well as on the policy:

- "This test was already failing before my change."
- "This failure is pre-existing."
- "This is unrelated to my implementation."
- "This is out of scope for this task."
- "This is a flaky test."
- "This is an environment issue, not a code issue."
- "I'll fix this in a follow-up."
- "Let's track this separately."

Why these claims are wrong on the facts: see "The baseline
assumption" above. The suite was green when this task started.
A failure now means either (a) your change broke it, (b) a
dependency or environment shift broke it AND your task is the one
that has to absorb the fix, or (c) the test is genuinely flaky AND
fixing the flakiness is part of your task. There is no fourth option
in which the failure is "not yours."

Why these claims are wrong on the policy: even in the rare case where
a failure pre-dates your work, the policy says: fix it. The cost of
unblocking the build NOW is always smaller than the cost of letting
red tests accumulate, masking new regressions, and eroding trust in
the suite.

## Forbidden actions

- `@pytest.mark.skip` / `pytest.skip()`
- `@pytest.mark.xfail`
- commenting out the test
- deleting the test
- excluding the test file from a test config (`pyproject.toml`
  `[tool.pytest.ini_options]`, `pytest.ini`, `conftest.py` collect
  hooks)
- adding a `pytest.mark` filter that excludes the test from the
  default run
- any other mechanism that prevents the test from executing or from
  failing the build when it fails

The test exists because someone designed a behavior and wrote a check
for it. Unless a spec change has explicitly removed that behavior
(documented in `.kiro/specs/<feature>/` with the spec change visible),
the test must keep running and must keep enforcing the behavior.

## The only allowed path

There is exactly one way out of a red suite:

### Step 1: Understand

- Read the failing test, the source it exercises, fixtures, conftest,
  helpers, and any module imported transitively. Skip nothing.
- Run the failing test in isolation to capture the full error and
  stack trace. Apply `no-output-shortening.md` — read the full
  output, do not tail.
- Trace the test's intent through docstrings, comments, the spec
  document if any, and recent commit history of the test file
  (`git log -p -- <test-file>`).
- State, with evidence, what behavior the test is supposed to verify
  and what behavior it is currently observing.

### Step 2: Research the right fix

- Consult the relevant MCP doc servers (per `use-doc-mcp-servers.md`):
  AWS Doc, AWS IaC, Strands, AgentCore, AWS API.
- Consult `docs/` for project-specific design.
- Consult `docs/lessons-learned.md` for prior fixes of similar issues.
- Consider at least two candidate fixes. Compare them on
  maintainability, correctness, and alignment with `design-principles.md`.

### Step 3: Apply the fix

- Default location: the SOURCE code under test.
- Exception: if the test itself has a bug in its TEST LOGIC (not in
  its assertion expectations — assertion expectations encode the
  required behavior and must not be relaxed to make tests pass), fix
  the test logic.
- Apply `coding-standards.md`, `design-principles.md`, and
  `file-organization.md` to the fix.

### Step 4: Verify — locally on what you touched, in CI for the rest

- Re-run the previously-failing test alone. Confirm pass with full
  output captured: `python scripts/run_tests.py <that test>`.
- Re-run the tests AROUND it — the module, the package, whatever the fix
  could plausibly reach. Fixing one test sometimes breaks another, and this
  is where you catch that cheaply.
- The FULL suite is CI's verdict, not a local one
  (`ci-owns-the-test-suite.md`). Push the batch once and read the CI run:
  it runs every test with no fail-fast, so it reports every remaining
  failure at once. You still don't get to stop until every test passes —
  what changed is WHERE the whole-suite run happens, never WHETHER it must
  be green.
- **Fix every failure that run reports, in one pass.** A red CI run is a
  complete list; treating it as a queue to work one item at a time turns
  one run into five.
- While CI-OUTAGE MODE is declared the `pre-push` hook runs the full suite
  locally at push time, with bounded workers. That is the only sanctioned
  local full-suite run.

### Step 5: Document

- If the failure mode was non-obvious, append a lesson to
  `docs/lessons-learned.md` per `use-lessons-learned.md`.

### Step 6: Loop if needed

If anything is still red after Step 4, you have NOT understood the
root cause. Go back to Step 1. Repeat until the suite is green.

## When the failure really is environmental

Sometimes a test fails because of a missing dependency, a stale venv,
a missing credentials file, or a network-dependent service that's
unreachable. These are still YOUR problem to resolve before the task
is done:

- Missing dependency: add it to `pyproject.toml` and `pip install -e
  ".[dev,cdk]"`. The original test author assumed the dep would be
  present; if it isn't, the project's dependency setup is broken.
- Stale venv: rebuild it per `use-venv.md`.
- Missing credentials: confirm the test is supposed to require them
  (read the test). If yes, document the credential setup in
  `docs/forLLMConsumption.md`. If no, the test is over-coupled to
  external state and needs to be refactored to use mocks/fixtures.
- Network flakiness: convert to a mock/fixture so the test no longer
  depends on the network. Don't `xfail` and don't add retries — fix
  the root cause.

In none of these cases is "the test is flaky" or "the env is
broken" a stopping condition. Each is a fixable problem that falls
inside the scope of the current task by virtue of having surfaced
during the current task.

## Integration

- `no-guessing.md`: every claim about a test failure ("this fails
  because X") needs evidence — the actual error message, the line of
  code that produced it, the doc reference that confirms expected
  behavior.
- `no-output-shortening.md`: read full pytest output, not the tail.
- `coding-standards.md` + `design-principles.md`: govern HOW you fix.
- `post-activity.md`: the post-activity checklist runs the affected tests
  plus `run_checks.py`; this rule is what governs your behavior when
  that gate is red.
- `ci-owns-the-test-suite.md`: WHERE the run happens (affected tests
  locally, full suite in CI) and the requirement to fix every failure a
  run reports in ONE pass. That rule never softens this one: a failing
  test is still always fixed, never skipped, xfailed or deleted.
- `use-lessons-learned.md`: document non-obvious failures so the
  next agent doesn't repeat the same root cause.
```

### 8.25 `remote-ci-must-pass.md` (always) — NEW IN v2
```markdown
---
inclusion: always
---
# Remote Repository Operations Are Not Done Until CI Passes (CRITICAL)

Any operation that changes code on the remote repository — commit,
push, merge, rebase-and-push, PR merge — is NOT finished until the
corresponding CI pipeline (if one exists) has run to a successful
completion.

## Core rule

1. After any operation that updates the remote (push, merge, PR
   merge), determine whether the repository has a CI pipeline.
   - GitLab: a `.gitlab-ci.yml` exists, or the project has pipelines.
   - GitHub: workflows exist under `.github/workflows/`.
   - If there is genuinely no CI pipeline, the operation is finished
     once the push/merge succeeds. State that no pipeline exists.
2. If a CI pipeline exists, you MUST monitor it until it COMPLETES —
   no matter how long it takes. Do not declare the operation done
   while the pipeline is queued, running, or in any non-terminal
   state. Poll until it reaches a terminal state (success or failure).
3. Retrieve pipeline/run status and logs through the project's wrapper
   script (`scripts/github_wrapper.py` / `scripts/gitlab_wrapper.py`) —
   never `gh`, `glab`, or raw `curl` (see `use-git-wrapper-scripts.md`).

## On failure (the debugging loop) — ONE run in, ALL fixes out

The pipeline is built NOT to fail fast: every check group runs in its own
job, no `needs:` chain skips a sibling because another failed, and each job
hands its whole group to `scripts/run_checks.py`, which continues past a
failure and ends with a consolidated `=== FAILED CHECKS (n) ===` block
(PART 7). A red run is therefore a COMPLETE list of what is wrong, not the
first thing that went wrong.

That is a bargain, and this is your side of it. If the pipeline finishes in
a failed state:

1. **Enumerate before fixing anything.** Retrieve the full logs of EVERY
   non-successful job via the wrapper script — not just the first, not just
   the ones that look related. Within each, list every failing test and
   every failing check. Apply `no-output-shortening.md`: complete logs, not
   a tail. Do not start editing while you are still reading.
2. **Group by root cause, and write the grouping down.** Ten failures are
   usually two or three causes. Record
   `N failures across M jobs → K root causes` in your state, with each
   failure assigned to a group, and determine each cause with evidence (per
   `no-guessing.md`). Consult MCP doc servers and `docs/` as needed.
3. **Fix EVERY group** in the source, tests, or configuration — all of
   them, before the next push. Commit as you go; commits are cheap
   (`ci-owns-the-test-suite.md`).
4. **Verify locally what is cheap to verify**: the affected tests via
   `python scripts/run_tests.py`, or `python scripts/run_checks.py --group
   lint` for a lint break. Do not re-run the full suite locally to
   pre-check the pipeline.
5. **Push ONCE**, then monitor the new run to a terminal state.
6. Repeat only if the new run surfaces something genuinely new.

**Fixing one failure and re-pushing to discover the next is a violation of
this rule, not a work style.** Each avoidable run costs pipeline minutes
that are themselves the scarce resource the capacity ladder below exists to
cope with. Record every run you cause, with its purpose and what it
surfaced, so the run count is visible and reviewable. If one failure truly
cannot be diagnosed from the logs in hand, say so explicitly with the
evidence, fix everything else, and treat the extra run as a cost you are
consciously choosing.

This loop is the ONLY exit. You may not abandon a remote-changing
operation with a red or unfinished pipeline. "It will probably pass",
"the failure looks unrelated", and "I'll let CI sort it out" are all
forbidden — they violate `no-guessing.md` and this rule. Note that "the
failure looks unrelated" is also forbidden as a reason to fix only the
related ones: an unrelated failure is still on your list
(`tests-must-not-fail.md`).

## When CI CANNOT RUN AT ALL: the capacity ladder (CRITICAL)

This section governs the case where the pipeline is not red but ABSENT —
the account's CI minutes/quota are exhausted, or hosted capacity is
otherwise refusing work. It has THREE rungs and you take the FIRST one
that applies. Running CI locally is the LAST rung, never the first, and
choosing it out of order is a rule violation, not a shortcut.

### Rung 0 — PROVE it is a capacity refusal, structurally

Duration is NOT the signal and is forbidden as one: an unresolvable
action reference fails in ~9 seconds with an empty log archive, which
looks identical. Fetch the per-job listing WITH per-step detail
(`get-jobs <run-id> --steps`; the terse form cannot distinguish these)
and classify EVERY non-successful job:

| Shape | `conclusion` | runner name | labels | steps | Route |
|---|---|---|---|---|---|
| **(A) genuine code failure** — the DEFAULT for a red job that has a runner and steps | `failure` | non-empty | any | `> 0` | the debugging loop above. NEVER this section |
| **(B) refused hosted job** | `failure` | **empty** | a HOSTED label | `0` | this ladder |
| **(C) fallback job that never started** | queued or `cancelled` | **empty** | a FALLBACK-prefixed label | `0` | declare a wait budget, then triage the fallback |
| **(D) skipped by a job gate** | `skipped` | `None`/empty | a HOSTED label | `0` | evidence of NOTHING — ignore |

Two traps, both measured on a real implementation: **(D) mimics (B)
byte-for-byte** and is distinguished ONLY by `conclusion`, so classify on
`conclusion` FIRST; and **(C) mimics (B)** too, so a fallback-prefixed
label must never be read as evidence about the HOSTED quota — that
confusion is how the recovery path becomes unreachable. Quote the
`runner_name=… labels=… steps=N` lines verbatim. "CI won't go green" is
never the evidence.

### Rung 1 — is the CodeBuild fallback ALREADY IMPLEMENTED? Then USE it

Check, do not assume, in this order — cheapest first:

1. Does a mode variable exist? Read it through the wrapper
   (`get-variable`). Its presence, and its `updated_at`, are evidence.
2. Do the workflow files resolve `runs-on` through that variable? Parse
   them; a `runs-on` expression naming the variable is the mechanism.
3. Has the fallback ever DISPATCHED? One job, in any run, carrying a
   fallback-prefixed label AND a non-empty runner name proves the build
   project, the source credential and the webhook are all live.

**If it IS implemented, relocating the pipeline is MANDATORY and local
execution is FORBIDDEN.** Flip the mode variable to the fallback token,
CONFIRM-READ it (a write helper that probes-then-creates can fail
partially, so an exit code establishes nothing), then force a fresh
`runs-on` evaluation by PUSHING a new commit to the branch. The result is
a real pipeline run of the same workflow, so it DISCHARGES the Core rule
above with no exception, no local substitution and nothing to disclose.
Confirm the relocation landed: every job must show a fallback label WITH
a non-empty runner name. A flip with no subsequent fallback-labelled
assignment is an unfinished flip, not a remedy.

Two prohibitions while relocating, because both are
infrastructure-mutation capabilities rather than retries: do NOT re-run a
default-branch run and do NOT dispatch the pipeline workflow, where a
deploy job's gate is `dispatch || (push && default-branch)` — the first
disjunct names NO ref, so a dispatch deploys whatever branch it was
dispatched on. Push to the branch instead; a pull-request run leaves the
deploy stage `skipped`, which is what makes a push the safe route.

The mode variable is SHARED state read by every run of every branch, so a
flip relocates CI for every concurrent worker. Take the lock, record it as
a `DL-NNN` decision with the prior value, the new value and the driving
run id (`agent-state-convention.md`), and do not flip back while another
worker has fallback work in flight. Unwillingness to mutate shared state
is NOT a reason to skip this rung.

### Rung 2 — NOT implemented? FILE IT (once), via issue-intake

If Rung 1's checks show the mechanism does not exist, the durable remedy
is to have it built, and `docs/codebuild-ci-backup-mechanism.md` is what
a worker needs to build it. It is installed in every project set up with
these prompts (PART 12), it is deliberately project-agnostic — with
placeholders for every name the project must choose, a three-phase plan
where each phase ships alone, the runner-label contract, the refusal
classifier, the sizing arithmetic and a verification checklist — and its
existence means **nobody has to redesign the mechanism.** Point the issue
at it rather than restating the design or researching it afresh.

Read its §1 before filing: three of the four options it lists need no
engineering at all (pay the hosted overage, make the repository public,
go all-in self-hosted), and for some projects one of those is the right
answer. The issue should name the alternatives so whoever picks it up
makes a decision rather than assuming the build.

**Check for an existing issue FIRST — this filing happens at most once
per project.** Search open AND closed issues through the wrapper
(`list-issues`, including a closed-state query, plus a title/body search
on the mechanism's terms). A closed one is decisive too: closed-as-done
means Rung 1's checks were wrong — re-run them; closed-as-rejected means
the project has DECIDED against it, so go to Rung 3 and do not re-file.
If an open issue exists, do NOT file a second one — add a comment noting
this new occurrence (the run id, the head SHA, the date) so the issue
carries how often the outage bites, then go to Rung 3.

Only if no such issue exists, file ONE through the **issue-intake**
agent — never by hand, so the intake template, the labels and the
provenance are applied consistently. This filing is pre-authorised and
satisfies `issue-filing-discipline.md`: it is an OBSERVED defect (a
measured, quoted capacity refusal that blocked a real merge), the
fix-first evaluation resolves to OUT-OF-SCOPE (a multi-phase
infrastructure build with IaC, a credential and new workflow files
cannot be absorbed into the issue in flight), and it is additionally a
standing HUMAN-REQUEST from the project setup. Give the issue:

- the quoted refusal evidence from Rung 0 (the shape-(B) job block, the
  run id, the head SHA);
- what it blocked, and how often — link previous occurrences if the
  ledger or earlier comments record them;
- BOTH document paths, naming which is normative and which is reference;
- the provenance lines the filing gate requires — `Origin:` (this
  rule, plus the blocked run), `Subject:` (CI capacity fallback),
  `Filing-rationale:` (OUT-OF-SCOPE + HUMAN-REQUEST, with the sentence
  above);
- the honest cost note from the guide's §1: per-run compute is roughly
  2–3× hosted, so cost is NOT the reason to build it — a pipeline that
  STOPS is.

Then go to Rung 3. Filing is not a substitute for verifying the change
in front of you.

### Rung 3 — run the pipeline LOCALLY, as a disclosed workaround

Reachable only when Rung 1 found no implemented mechanism AND Rung 2 has
been discharged (an issue now exists, whether you filed it or found it).
It is NOT an exception to prove-before-merge — it REPLACES remote CI with
a complete local execution of the same pipeline. This is the ONE state in
which the full test suite runs locally, and even here it runs at PUSH
time, never at commit time (`ci-owns-the-test-suite.md`).

0. **DECLARE the outage** so the mechanism knows, rather than relying on
   you to remember:
   ```bash
   python scripts/ci_outage_mode.py declare --evidence-run <run-id> \
       --issue <n> --rung 3
   ```
   It writes a marker into the SHARED git dir, so ONE declaration covers
   every concurrent per-issue worktree in the clone — a per-worktree
   marker would leave sibling runs pushing unverified code. From that
   moment the `pre-push` hook runs the full suite on every push, and
   `declare` refuses without the evidence run id and the Rung 2 issue,
   which is how the disclosure material in step 4 gets captured at the
   moment it is still in front of you instead of reconstructed later.
1. Run EVERY job group of the workflow locally, inside the venv
   (`use-venv.md`), reading complete output (`no-output-shortening.md`):
   ```bash
   python scripts/run_checks.py
   ```
   This is the SAME script each CI job runs (PART 7), so the local mirror
   cannot structurally drift from the pipeline — you are not
   reconstructing it, you are running it. It also does not stop at the
   first failure, so one local pass gives you the whole list, exactly as
   a real run would. Treat any failure exactly as a red CI: fix every
   root cause in one pass, never skip.
   *If this project's CI does NOT route through `run_checks.py`, fall
   back to deriving the command list FROM the workflow file, and say so
   in the disclosure — a hand-derived mirror can drift and the reader
   needs to know which kind they are being shown.*
2. Any step that genuinely cannot run locally (a missing toolchain that
   cannot be installed, a credentialed deploy job) is a DISCLOSED GAP:
   name the step and the reason. "Best-effort" means you disclose the
   gap, never that you silently skip it.
3. Run against the SAME head SHA that is being merged.
4. Then, and only then, merge — and post a comment on the PR/issue
   stating: that remote CI could not produce a run, with the quoted
   shape-(B) evidence; that the fallback mechanism is not implemented,
   with the issue number from Rung 2; the head SHA; the pass result of
   every local job group; and every gap. Do not assert "quota
   exhaustion" unless that is what the evidence says.
5. Disclose every job of the merged run that did not execute. Once
   capacity returns, the normal rule resumes and a later run must
   confirm green — and **clear the marker at that moment**:
   ```bash
   python scripts/ci_outage_mode.py clear
   ```
   Clearing is not housekeeping. While it is set, every push in every
   worktree of this clone pays for a full local suite, which is the cost
   this whole rule set exists to avoid.

### What is NOT this ladder

- A red run WITH a runner and steps and a named failing step — shape
  (A), the debugging loop, whichever runner it ran on.
- A job `cancelled` at its timeout with no summary line, or a
  broken-pipe/decode error from a heavy library's child process. Both are
  measured RESOURCE-CEILING signatures whose remedy is a size or
  worker-count edit, never a merge.
- A permission error from a billing endpoint. If the token lacks the
  billing scope its failure is evidence in NEITHER direction.
- "The flip did not seem to take", "the fallback would probably have
  worked", "the hang was infrastructure, so I ran it locally." Each is a
  `no-guessing.md` violation wearing this section's clothes.
- Skipping Rung 1 because the check "would probably" show nothing, or
  skipping Rung 2 because filing feels like overhead. Both rungs are
  mandatory and both are cheap.

## Evidence required to declare success

State the terminal pipeline status with evidence quoted from the
wrapper output: pipeline/run ID, status (`success`/`passed`), and the
commit SHA it ran against. Without that evidence, the operation is not
finished.

## Integration

- `use-git-wrapper-scripts.md`: all CI status/log retrieval goes
  through the wrapper.
- `no-output-shortening.md`: read complete CI logs.
- `no-guessing.md`: every claim about pipeline state is backed by
  quoted wrapper output — including each rung's determination in the
  capacity ladder.
- `issue-filing-discipline.md`: Rung 2's filing is pre-authorised by
  this rule (OUT-OF-SCOPE + HUMAN-REQUEST) and still carries the
  provenance lines the filing gate checks. It is a once-per-project
  filing, so the duplicate check is mandatory.
- `agent-state-convention.md`: the mode-variable flip is a shared-state
  mutation — take the lock and record it as a `DL-NNN` decision.
- `continuous-work.md`: a capacity outage is NOT a hard blocker while a
  rung remains untried. Work down the ladder rather than stopping to ask.
- `ci-owns-the-test-suite.md`: the other half of this rule. It owns WHERE
  tests run (affected tests locally, full suite in CI), the commit-often /
  push-once contract, the bounded local worker count, and the CI-outage
  marker this rule declares at Rung 3. A pipeline that is scarce enough to
  need a capacity ladder is a pipeline whose runs must not be spent on
  one-failure-at-a-time debugging.
- `always-test-e2e.md`: a remote change that triggers CI is part of
  the E2E loop; the E2E test is not complete until CI is green.
- `docs/codebuild-ci-backup-mechanism.md` is installed by PART 12 and is
  what Rung 2's issue points an implementer at, so the mechanism never
  has to be redesigned per project.
- The `git-push` hook (Part 9) implements this rule operationally.
```

### 8.27 `agent-state-convention.md` (always) — fleet convention

This rule and 8.28–8.32 are the always-loaded conventions the Kiro CLI
custom-agent fleet (installed in PART 8A) depends on. They apply to EVERY
agent. Create each as a steering file with `inclusion: always` (no front
matter is also fine — absent front matter means `always`) — except 8.31,
which is `fileMatch`-scoped.

```markdown
---
inclusion: always
---
# Agent State & Decision-Log Convention (ALL agents)

Every Kiro CLI custom agent keeps its resume/log artifacts under
`.kiro/agent-state/<agent-name>/` (`<agent-name>` = the agent's `name`, e.g.
`spec-conductor`, `dead-code-removal-agent`). Typical artifacts: `resume_state.md`
(Status + phase + counters + git HEAD + source mtimes), `iteration_log.md`,
`evidence_ledger.md`. Create the directory (and parents) on first use. Archive a
completed/stale artifact by suffixing an ISO timestamp; never delete history.
`.kiro/agent-state/` is gitignored (per-run runtime state).

## Per-run namespacing when multiple runs share one clone
A single-run agent uses the flat layout above. An agent of which **multiple
instances may run concurrently in one clone** (notably `issue-work-orchestrator`)
MUST namespace its state per run so runs never share a `resume_state.md` slot:

    .kiro/agent-state/<agent-name>/
      registry.json            # session_id -> { run_id, session_id, cwd, state_dir,
                               #                 current_issue, status, started_at, last_heartbeat }
      .locks/<resource>.lock   # per-resource mkdir locks (atomic create-or-fail; NTFS-safe)
      runs/<run-id>/           # ONE run's private state subtree
        resume_state.md  workflow_state.md  environment.md  issue_queue.md  iteration_log.md

Run identity is established by an **agentSpawn hook** (`kiro-session-register.sh`,
installed in PART 8A) that writes `registry.json` keyed by the `session_id` Kiro
passes on stdin; `run_id` is derived from it. The agent and the gate hooks both
resolve "which run owns this session" via that registry — no environment variable
carries identity (consistent with `no-environment-vars`).

**How far that resolution holds differs PER HOOK, so keep every run's state at the
registry-derived path.** `kiro-loop-gate.sh` is session-keyed and nothing else: the
registry's `state_dir`, else `runs/<first-8-of-session_id>/`, and it exits 0 — a silent
no-op — when no `resume_state.md` is there. `kiro-stop-gate.sh` and `kiro-tdd-gate.sh`
prefer that same lookup but FALL BACK to `ls -t` over every `workflow_state.md` under
`.kiro/agent-state/`, taking the most recently modified one; `kiro-continuous-work-reinject.sh`
falls back the same way to the most recently touched `runs/*/`. **RESIDUAL, stated because it
is not fixed:** with two runs live in one clone those three can read a SIBLING's state — the
spec gate then judges this run against a stranger's phase and evidence, and the re-inject
announces a stranger's issue, branch, worktree and PR as "your recorded place in the work".
That second harm was MEASURED (on the Claude Code hooks, which were then rewritten to have no
mtime rung at all; this port does not carry that rewrite): a session working one issue was
told its current issue was another run's, and had to be corrected twice. Note also that every
registry lookup here, and the register hook's own write, sit inside `command -v jq` with no
fallback — so on a host without `jq` no entry is written at all, and while the loop gate and
the re-inject can still derive `runs/<first-8-of-session_id>/` from the session id itself, the
two spec gates cannot: for them the mtime scan is then the ONLY resolution. Install `jq`
before running two orchestrators in one clone, and read any gate verdict in a concurrent clone
as unattributed until you have checked WHICH file it read.

## The decision log (mandatory for all agents)
Whenever an agent makes a non-trivial decision (a design choice, a classification, a
fix approach, a convergence/exit call, an escalation) it appends one entry to a
decision log: to `.kiro/specs/<feature>/decisions/decision-log.md` if operating in a
spec context, else to `.kiro/agent-state/<agent-name>/decision-log.md`. Entry schema
(append-only, monotonic `DL-NNN` IDs, never reused):

    ## DL-<nnn> — <ISO-timestamp> — <agent-name> — phase:<PHASE-or-"n/a">
    **Decision:** <one sentence>
    **Driver:** <requirement IDs, finding IDs (A2/B1), user answer, a failing test, an MCP source>
    **Alternatives considered:** <one line each, or "none">
    **Evidence:** <path:line | evidence/... | review/<r>/iteration-NN.md#A2 | MCP/web citation>
    **Supersedes:** <DL-mmm, or "none">
    **Artifacts touched:** <files written/edited>

Rules: append-only (to change a past decision, write a NEW entry whose `Supersedes:`
points at the old one); every entry cites concrete evidence (a decision with no
citable driver is itself a defect); record decisions, not narration. **Under
concurrency:** when multiple runs could append to the SAME log, give each run its OWN
`runs/<run-id>/decision-log.md` to avoid duplicate IDs; the agent-root log is reserved
for cross-run notes.
```

# No AI Attribution; Descriptive Names Only (ALL agents)

### 8.29 `keep-git-clean.md` (always) — fleet convention

```markdown
---
inclusion: always
---
# Keep Git Clean and Up-to-Date (ALL agents)

The local git repository must never be left messy or stale. At every phase boundary,
and ALWAYS when an issue/PR/task reaches a terminal state, the working tree must be
clean (`git status --porcelain` empty) except for deliberately-in-progress files, with
no stale branches or worktrees.

**COMMIT** (belong in version control): source, tests, configuration
(`pyproject.toml`, `.pre-commit-config.yaml`, CI config), the tracked git hooks
(`.githooks/`), the secret-scan baseline (`.secrets.baseline` — it is the audited
allow-list, so without it the pre-commit hook fails on every clone), docs, IaC/CDK,
scripts, spec artifacts kept under version control, `.gitignore`/`.gitattributes`.
**NEVER COMMIT** (auto-generated/transient/machine-local): build/compiled output
(`build/`, `dist/`, `*.egg-info/`, `*.pyc`, `__pycache__/`), caches (`.pytest_cache/`,
`.mypy_cache/`, `.ruff_cache/`, `.hypothesis/`), coverage (`.coverage`, `htmlcov/`),
check/test reports written by `scripts/run_checks.py` and `scripts/run_tests.py`
(`reports/`), venvs (`venv/`, `.venv/`), editor/OS cruft, secrets/credentials, anything
under `tmp/`, generated version files (`src/_version.py`), and per-run agent state
(`.kiro/agent-state/`, `.kiro/worktrees/`). If a never-commit file is not already
ignored, ADD it to `.gitignore` rather than leaving it untracked. Never `git add -A`
blindly — committing often (`ci-owns-the-test-suite.md`) is encouraged and is NOT a
licence to skip this classification.

## Worktrees and branches
- Per-issue/per-task worktrees and branches are EPHEMERAL: when work reaches a
  terminal state, `git worktree remove <path>` and `git branch -d/-D`, and verify
  nothing is left behind. The clean end-state is **per run**.
- **Do NOT move the shared local `main` branch.** When multiple runs may share one
  clone, a run NEVER `git checkout main`s or fast-forwards local `main`. Fetch and
  base new worktrees on `origin/<main>`, and verify merges with
  `git merge-base --is-ancestor <sha> origin/<main>` instead of advancing local `main`.
- Never leave a detached HEAD, half-finished rebase/merge, or orphaned worktree.

## Concurrency-safe maintenance
The one genuine corruption risk when several worktrees share one object store is
concurrent auto-gc, which `git fetch` can trigger. Set ONCE on the clone (idempotent):
`git config gc.auto 0`, `git config maintenance.auto false`,
`git config gc.autoDetach false`. Pass `--no-auto-gc` on every fetch
(`git fetch origin --prune --no-auto-gc`); NEVER `--prune=now` or a manual `git gc`
while any worktree operation may be in flight. (`--no-auto-maintenance` is NOT a valid
fetch flag on git ≥ 2.51 — use `--no-auto-gc` plus the persistent config.)

## Stay up-to-date
Integrate remote changes regularly. Any conflict is resolved per the line-by-line
merge discipline — delegate to the `code-merge-reviewer` agent where installed; never
blind "take theirs/ours".

# Issue Tracking: Checklists, Metadata, and Live Updates (ALL agents)

Shared by every agent that touches the issue tracker (issue-intake,

operations go through the project's git wrapper script (`use-git-wrapper-scripts`).

  record the current branch/worktree/PR and the spec/evidence location.
- **Q&A always on the issue:** any question put to the user about an issue and the

  the whole set and silently drops other labels (this repeatedly caused duplicate work).
  Use additive `issue label-add`/`issue label-remove` for label changes; `issue release`
  to drop a claim you can't act on now.
- **Closing:** close with a final comment linking the merged PR/MR and evidence,
  ensure the checklist is fully ticked (or remaining items deferred with a reason),

  route it through `issue-filing-discipline.md` (fix it now, one gated issue, or a

### 8.31 `per-worktree-venv.md` (conditional, CDK / app files) — fleet convention

```markdown
---
inclusion: fileMatch
fileMatchPattern: "cdk/**"
---
# Per-Worktree Virtual Environment (when running code/CDK from worktrees)

Applies to projects that **execute code or IaC from inside a git worktree** while
concurrent runs share one clone — most importantly AWS/CDK projects
(`cdk synth`/`cdk deploy`) and any project importing an editable-installed package.
For pure-library projects that only run tests from the main checkout, this is not
needed.

**Why:** a git worktree isolates the working tree, index, and branch — but a single
shared venv does NOT. A `pip install -e` writes ONE editable `.pth` pinned to the
absolute path of the checkout it ran in; code/CDK run from a worktree on that shared
venv import the OTHER checkout's `src`/`cdk`. Re-running `pip install -e` against the
shared venv to "fix" imports rewrites that one `.pth` last-writer-wins, corrupting
every other concurrent run.

**The rule:**
1. Each worktree that will run code/CDK gets its OWN venv: after `git worktree add`,
   create `<worktree>/venv` and `pip install -e ".[dev,cdk]"` INSIDE the worktree.
2. Invoke tools by the worktree's ABSOLUTE interpreter
   (`<worktree>/venv/Scripts/python.exe -m <tool>` on Windows,
   `<worktree>/venv/bin/python -m <tool>` on *nix) with `cwd = <worktree>`; do not rely
   on activation.
3. NEVER "fix" imports by re-running `pip install -e` against the SHARED venv.
4. Authoritative self-check (not vacuous): read the worktree venv's `*.pth` and confirm
   it contains the WORKTREE path; for CDK, a real `cdk synth` that resolves
   `cdk.__file__` under the worktree. Make this a resume precondition.
5. Teardown (Windows): delete `<worktree>/venv` BEFORE `git worktree remove` (locked
   DLLs otherwise block removal), or use out-of-tree worktrees.
6. Bound concurrency (`MAX_CONCURRENT_WORKTREE_RUNS`, ~1.5 GB/venv) and pass an
   explicit `pip --cache-dir <worktree>/.pipcache` (do NOT set `PIP_CACHE_DIR` — env
   vars are forbidden).
```

### 8.32 `issue-filing-discipline.md` (always) — fleet convention — NEW

```markdown
---
inclusion: always
---
# Issue Filing Discipline: fix it, or file it — never file by default (ALL agents)

An autonomous issue-driven workflow spawns its own backlog: verification finds defects,
evidence culture forbids dropping them, every finding becomes a tracker entry, every
entry gets worked, and working it runs the discovery engine again. Measured on a project
built with this setup: 60% of all issues (78% in the last measured month) were created by
working other issues, weekly creation went 11 → 52, and the subject mix moved from the
product to the workflow machinery. No single filing was wrong; the DEFAULT was. Filing an
issue is not the cheap, diligent option — it commits a future work cycle and needs a
reason.

**Only an OBSERVED defect can be filed.** Evidence you can quote: failing command output,
a wrong value, an exception, a cited code path whose misbehavior you demonstrated. NOT
defects: "this could go wrong", "not hardened against X", "a guard is missing", "looks
fragile", a theoretical race, an unexercised edge case, a stylistic preference.

**Zero filed issues is a valid and expected outcome.** Never file to demonstrate
diligence or to record that you looked. A run that fixed its issue and filed nothing is
complete — say so plainly.

**No quotas.** No agent has a per-run filing target ("file N proposals", "one issue per
finding"). A sweep that finds nothing filable reports exactly that.

**The fix-first evaluation (MANDATORY before any filing).** Stop at the first branch that
applies and record which one:
1. **Blocking the current task?** → fix it inside the current change.
2. **Small and clear?** → **FIX IT NOW; do not file.** Localized, a few lines, no design
   choice, no new dependency, no public-API/schema change, provable with the existing
   tests plus at most one added test. Typos, off-by-ones, wrong constants, missing None
   checks, stale docstrings: fix, mention in the commit message and the report.
3. **Needs one of these three?** → file, and NAME it: `RESEARCH` (solution needs
   extensive investigation), `DESIGN-OPTIONS` (alternatives to evaluate / a spec cycle),
   `OUT-OF-SCOPE` (fixing it here would materially enlarge the change or reach unrelated
   subsystems). A human asking for an issue is its own rationale: `HUMAN-REQUEST`.
4. **None of the above?** → one row in `docs/findings-ledger.md`, then move on.

**Process machinery needs a NAMED INCIDENT.** A gap in a hook, gate, rule, lock protocol,
CI script, or agent prompt is filable only after it caused measured damage (lost work, a
false merge, a false block, corrupted state, a wedged session). Name it, or ledger it and
wait. Guards ship at "good enough"; adversarial completeness is for the product.

**Already resolved is never filed.** Report the proof; do not create a tracker record of
a non-defect for someone to close.

**Check duplicates and neighbors first** (open AND recently closed) and extend the
existing issue instead of opening a sibling. **One observation → at most one issue**; no
"companion" issues for discarded candidates.

**Route every filing through the `issue-intake-agent`** rather than calling the tracker
yourself; call the wrapper's `create-issue` directly only when intake is unavailable, and
then produce the same body.

**Mandatory provenance lines in every filed body** (the `preToolUse` gate
`.kiro/hooks-bin/kiro-issue-filing-gate.sh` blocks a create call without them):

    Origin: human-request | spawned-discovery | spawned-residual | agent-sweep
    Subject: product | process
    Spawned-from: #<N>          (required when Origin is spawned-*)
    Filing-rationale: RESEARCH | DESIGN-OPTIONS | OUT-OF-SCOPE | HUMAN-REQUEST — <one line>

`Subject` is `product` if the change can alter behavior a user of the delivered system
experiences (the tie-break for deploy/build tooling), else `process`.

**The findings ledger** `docs/findings-ledger.md` is the durable home for everything NOT
filed: sub-threshold findings, theoretical hardening gaps, adjacent observations,
deferred checklist items. Append-only, same evidence standard as an issue, no obligation
of work — this is what makes "nothing may be dropped" compatible with "do not file it".
Columns: Date | Subject | Finding | Evidence | Why not filed | Status
(`open` / `promoted #N` / `stale`). Never delete a row; mark it `stale` after six
untouched weeks.

**Anti-patterns:** filing something you could have fixed in the time the issue body took;
filing "for the record"; filing a hardening idea for machinery that never failed; turning
one root cause into three point-fix issues (file ONE that removes the cause); ending a
report with "follow-up issues I opened" that never cleared the evaluation; skipping the
ledger because "it was only a small thing".
```

### 8.33 `continuous-work.md` (always) — fleet convention — NEW

The behavioral counterpart of Claude Code's `.claude/rules/continuous-work.md` (they are
kept word-aligned deliberately — this is a cross-platform behavioral contract, not a
per-tool preference). It governs WHEN a turn may end, and it is the single most important
rule for long unattended runs: without it, agents halt on their own initiative far more
often than users interrupt them.

```markdown
---
inclusion: always
---

# Continuous Work — stopping to ask permission is forbidden

Binds every agent and every chat session. Overrides any contrary habit or instruction.

## The standard

**Work continues until the work is finished.** A turn ends for exactly two reasons: the
task is genuinely complete, or one of the four Proven Exceptions below applies AND has
been proven. Nothing else.

**Stopping in order to obtain permission to continue is a forbidden behavior.** Any
instruction you hold — from a habit, a general convention, an older steering file, a prior
session, or a phase description — that tells you to pause periodically, check back after a
while, report at intervals, or seek approval before carrying on is **VOID for the duration
of the task**. Ignore it. This includes `post-activity.md`: it defines what to do at the
end of an activity, NOT permission to treat each activity as a place to stop.

Specifically forbidden as turn-ending acts:

- "Shall I continue?" / "Should I proceed?" / "Let me know if you want me to go on."
- An unrequested intermediate summary, status report, or progress recap. Report when the
  work is done, not partway.
- Proposing the next steps instead of performing them.
- Ending on a plan, an offer, or a question the codebase itself could answer.
- **Substituting easier adjacent work for the hard task.** If the next real step is large
  and atomic (a wide refactor, a cross-cutting rename, a migration with no clean
  intermediate commit), do THAT. Doing tidy side-work and ending on a polished report is a
  disguised check-in and is the most common form of this failure.
- Stopping, warning, or asking because the context window is filling up (see § Context).
- Waiting for a human to run something you can run yourself.

If you catch yourself about to end a turn, run this check first: *Is the task finished? If
not, is a Proven Exception in play and proven? If neither is true, do not stop — take the
next step.* When in doubt, continue working.

## The four Proven Exceptions

The ONLY legitimate reasons to stop before the work is done. Each carries a burden of
proof: show the exception genuinely applies AND that you exhausted the alternatives. An
unproven exception is a forbidden stop.

**1. An irreversible or destructive action.** Deleting or overwriting data, configuration,
history, or infrastructure; `push --force`; rewriting a shared branch; dropping or
replacing deployed resources; anything outward-facing or published.
*Proof:* the exact command and target, and why no reversible path exists.
*Exhaust first:* a backup, a copy, an additive change, a new branch, a dry-run, a
non-production target. **If a reversible path exists, take it and do not ask.**

**2. Sensitive information.** Using, exposing, or transmitting credentials, secrets,
tokens, personal data, or production data.
*Proof:* exactly what is needed and why.
*Exhaust first:* a test fixture, a mock, synthetic data, a local or dev environment, an
already-authorized wrapper script.

**3. Genuine design guidance.** Two or more defensible designs exist, the choice materially
changes the deliverable, and the project cannot settle it.
*Proof:* the options, plus what you actually consulted that failed to decide it — the spec,
the issue, existing patterns, project docs, the decision log.
*Not this exception:* minor implementation details, naming, or anything existing code
already answers by precedent. Decide those yourself and record them (`DL-NNN`).

**4. A hard blocker.** Missing credential or authentication material, missing access, an
unavailable external service, or a missing required capability (e.g. a wrapper subcommand
that does not exist).
*Proof:* the exact failing command with COMPLETE output (`no-output-shortening`), plus the
alternatives tried.
*Not this exception:* a failure you have not yet diagnosed. Diagnose it first — a red test
or a red pipeline is work to do, not a blocker to report.

Before invoking any exception you must have researched the project's docs and code, the
relevant MCP documentation servers, the spec/issue, and git history. "I am not sure" is not
proof — it is an instruction to go find out (`no-guessing`).

## How to ask, when an exception is proven

- **Be short.** Two sentences of context, the options, the recommendation. Five lines is
  plenty. No preamble, no recap of what you already did.
- **Always give a recommendation.** Never present a bare choice; state which option you
  would take and the one reason why. A question without a recommendation is incomplete.
- **Batch.** One message with every open question. Never drip-feed.
- **Record it durably.** Put the question and its answer where the work lives — a comment
  on the issue (`issue-tracking`) or the spec's `qa_log.md` — not only in chat, which does
  not survive compaction.
- **Keep working.** After asking, continue with every part of the task that does not depend
  on the answer. Asking is never a reason to idle.

## Context-window pressure is never a reason to stop

Compaction is automatic: older history is replaced by a structured summary of goals,
decisions, progress and next steps while recent messages stay verbatim, and the session
continues with no interruption. **You cannot trigger it yourself** — manual `/compact`
exists only as a user command in the CLI, and the IDE has no manual trigger at all. So
never stop, never warn, never ask about context. Just keep working.

Your obligation is to make compaction lossless:

- **Externalize state continuously.** Write progress, decisions, the current phase, and the
  next step to the durable state files (`agent-state-convention`) after EVERY step — never
  hold your place only in the conversation. On-disk state is what survives.
- Keep the issue or spec updated as the live record, so the work is reconstructible from it
  alone.
- **Delegate large reads** to a subagent so file contents land in its context, not yours.
- **After a compaction, re-read before acting:** your state file, the active spec's decision
  log, and any file you still need. `inclusion: always` steering (including this file)
  stays in effect; `fileMatch` steering returns when you next touch a matching file.
  Compacted history is unrecoverable within the session, so anything that must outlive it
  belongs on disk or on the issue. Then resume the recorded step; do not restart the task.

## Enforcement

`kiro-loop-gate.sh` (the CLI `stop` hook) mechanically blocks turn-end while an
orchestrator run has workable issues remaining, and the user can restart a stalled run with
`@continue-work`. Neither substitutes for this rule: the gate covers only the orchestrator
loop and yields after `LOOP_BLOCK_CAP` consecutive blocks, so everywhere else this rule is
the only thing standing between a long run and an unnecessary halt.
```

### 8.34 `ci-owns-the-test-suite.md` (always) — fleet convention — NEW

This is the rule that decides where the project's test suite executes. It is
the companion of 8.25 (`remote-ci-must-pass.md`), which governs the CI run
itself, and it is the reason PART 2's hooks and PART 7's pipeline are shaped
the way they are. Install it as a steering file with `inclusion: always`.

```markdown
---
inclusion: always
---
# CI Owns the Test Suite — commit cheaply, push once, fix everything (ALL agents)

This rule governs WHERE tests run, WHEN you may push, and WHAT you must do
with a red CI run. It is the companion of `remote-ci-must-pass.md`, which
governs the CI run itself.

## Why this rule exists

Three measured failures of the previous arrangement, in which the full suite
was a precondition for every commit:

1. **Commits cost an hour.** On a project whose suite runs for 60 minutes, a
   per-commit suite made each commit a 60-minute operation. Agents responded
   rationally: they stopped committing, batched an entire feature into one
   enormous commit, and the history became unreviewable — the exact opposite
   of what a commit gate is for.
2. **The machine died.** `pytest -n auto` takes one worker per vCPU. Several
   concurrent per-issue worktrees each doing that made the host unusable and
   got the agent process killed mid-run, losing the work.
3. **Fail-fast turned one run into many.** A pipeline that stops at the first
   failing stage reports ONE problem per run. The worker fixed it, pushed,
   waited, found the next, and burned a full cycle per failure. Ten failures
   meant ten pipeline runs.

None of that bought any correctness. A local suite run and a CI suite run on
the same SHA prove the same thing, and only one of them is free.

## Where things run

| Boundary | What runs | Cost |
|---|---|---|
| `pre-commit` hook | ruff lint, ruff-format, bandit (staged files), secret scan | < 2 s |
| `pre-push` hook | mypy | seconds |
| `pre-push` hook, **CI-OUTAGE MODE declared** | mypy + full suite, bounded workers | the exception |
| CI | every check + the full suite, **no fail-fast**, all failures reported together | authoritative |
| you, locally, while working | the AFFECTED tests — `python scripts/run_tests.py <paths or -k expr>` | your call |

**The full test suite is never a precondition for a commit.** Not by a hook,
not by a gate, not by your own discipline. If you are about to run the whole
suite so that you are allowed to commit, that is this rule being violated.

## Commit often; push once

- A commit costs about a second. Commit at every natural boundary — a task
  finished, a test written, a refactor separated from a behaviour change. A
  readable series of small commits is the deliverable, not an accident.
- **The push is the batching boundary.** Push when the batch of work is
  complete and self-consistent, not when you want to know whether it works.
  Never push "to see if CI passes" — that is the trial-and-error loop this
  rule exists to end.
- Before a push you owe: the paired tests for what you built, green,
  captured. You do NOT owe a local full-suite run. CI runs the suite on the
  pushed SHA and that run is the authoritative verdict.
- `--no-verify` is forbidden on both commit and push. At commit the hook is a
  second of lint and secret scanning, so there is nothing to save; at push it
  is the only local gate there is. `kiro-tdd-gate.sh` blocks both.

## Local test execution is bounded

When you do run tests locally, go through `python scripts/run_tests.py`. It
derives a BOUNDED worker count — `min(4, cores // 4)`, floor 1 — and refuses
`-x` / `--maxfail`.

- **Never `pytest -n auto` locally.** That is a CI-runner setting.
  `run_tests.py --workers auto` exists for CI and nothing else.
- **Never run suites in two worktrees at once.** The bound is per process;
  four worktrees at four workers each is sixteen pytest processes, which is
  how the host became unusable.
- If a suite is flaky under parallelism, `--workers 1` is the honest answer
  while the shared state gets fixed — not a retry loop, and never an `xfail`
  (`tests-must-not-fail.md`).

## One CI run per fix batch (the discipline that matters most)

CI runs every check and reports every failure in a single run — that is what
`scripts/run_checks.py` is for, and why no CI job may be a multi-command step
list. Your side of that bargain: **use the whole report.**

When a CI run comes back red:

1. **Enumerate completely first.** Retrieve the logs of EVERY non-successful
   job through the wrapper script, and within each, every failing test and
   every failing check. Read complete output (`no-output-shortening.md`). Do
   not start fixing while you are still reading.
2. **Group by root cause.** Ten failures are usually two or three causes.
   Write the grouping down: `N failures across M jobs → K root causes`.
3. **Fix every group.** All of them, in this working session, before you push
   again.
4. **Push once.** Then monitor that run to a terminal state.

**Fixing one failure and re-pushing to find the next is a rule violation, not
a work style.** So is "I'll fix the obvious one and see what's left." If a
failure genuinely cannot be diagnosed from the logs you have, say so
explicitly with the evidence, fix everything else, and treat the extra run as
a cost you are consciously choosing.

Record each CI run you cause in your run state with its purpose and what it
surfaced (run id, why you pushed, failures found, root-cause groups). The
count is the metric: a fix that took four runs when it could have taken two
is a defect in how the work was done, and without the record nobody can see
it.

## When CI cannot run at all

That is `remote-ci-must-pass.md`'s capacity ladder, not this rule's business —
with one mechanical consequence that lives here: while the outage lasts, the
suite runs at PUSH time, never at commit time.

```bash
python scripts/ci_outage_mode.py declare --evidence-run <id> --issue <n> --rung <2|3>
python scripts/ci_outage_mode.py clear      # the moment a real CI run goes green
```

`declare` writes a marker into the SHARED git dir, so one declaration covers
every concurrent worktree in the clone, and the `pre-push` hook picks it up
with no further configuration. Clearing it is not housekeeping: while it is
set, every push in every worktree pays for a full local suite.

## Self-check

Before pushing, confirm: paired tests green and captured; the batch is
complete rather than a probe; no `--no-verify` anywhere; no local full-suite
run was performed to satisfy a gate. After a red CI run, confirm: every
failing job read, every failure enumerated, root causes grouped and written
down, all of them fixed, exactly one push.

## Integration

- `remote-ci-must-pass.md`: the CI run itself — monitoring it, the debugging
  loop, and the capacity ladder when it cannot run. This rule says what you
  do with its output.
- `tests-must-not-fail.md`: a failing test is always fixed, never skipped or
  xfailed. That is unchanged and unconditional; this rule only changes WHERE
  the run happens.
- `post-activity.md`: the completion checklist runs the affected tests
  locally and takes the suite verdict from CI.
- `keep-git-clean.md`: commit only what belongs — a frequent-commit habit is
  not a licence to commit generated files or `reports/`.
- `continuous-work.md`: waiting for a CI run is not a reason to end a turn.
  Monitor it, and work on anything that does not depend on its result.
- `no-output-shortening.md` / `no-guessing.md`: "every failing job" means
  every log read in full, and every claim backed by quoted output.
- `use-venv.md`: every local run happens inside the venv.
- `scripts/run_tests.py`, `scripts/run_checks.py`, `scripts/ci_outage_mode.py`:
  the mechanisms (PART 2). `run_checks.py` is the same command CI runs, which
  keeps a local pipeline execution from drifting away from the real pipeline.
```

What each does (the agents' `hooks` blocks already reference them, so no further
wiring is needed beyond the copy):

- `kiro-session-register.sh` — `agentSpawn` hook on `issue-work-orchestrator`. Records
  this run's identity (session_id, cwd) into
  `.kiro/agent-state/issue-work-orchestrator/registry.json` so concurrent runs and the
  gate hooks can tell which run owns which issue.
- `kiro-continuous-work-reinject.sh` — `agentSpawn` hook (wire it alongside
  `kiro-session-register.sh` on the orchestrator, conductor, and implementer). Its STDOUT is
  added to the agent's context on spawn, so it prints the `continuous-work` contract plus
  THIS run's recorded place in the work — phase, current issue, branch, worktree, PR,
  `WORKABLE_ISSUES_REMAIN`, `AWAITING_USER`, read out of the run's `resume_state.md` located
  through the registry (then `runs/<first-8-of-session_id>/`) — and flags an uncommitted tree
  as work-in-progress rather than a stopping point.
  Read-only and fail-quiet: with no state it prints the contract alone. **Its last rung is
  NOT session-keyed:** when neither of those resolves it takes the most recently touched
  `runs/*/`, so in a clone with a concurrent run it can present a SIBLING's issue, branch,
  worktree and PR as this run's own — the residual named in steering 8.27, and the reason the
  registry-derived path is not optional here.
  **Kiro limitation, stated plainly:** Kiro has no compaction hook, and automatic compaction
  continues the SAME session, so `agentSpawn` does NOT re-fire after it. This covers launch
  and relaunch only. Mid-session the `inclusion: always` steering file keeps the CONTRACT in
  context (Kiro's advantage over Claude Code here) while the state files keep the POSITION,
  and `@continue-work` is the manual recovery path. Claude Code's twin additionally binds to
  `SessionStart` matcher `compact`, which Kiro has no equivalent of.
- `kiro-tdd-gate.sh` — `preToolUse` hook (matcher `execute_bash`) on the orchestrator,
  conductor, and implementer. Exit code 2 BLOCKS: a `git commit` using `--no-verify`/`-n`;
  a `git push` using `--no-verify`; a `git push` while a task marked complete has no test
  capture, or the newest paired-test capture is red or full of skips; and a `git push`
  while CI-OUTAGE MODE is declared with no green full-suite capture.
  It gates PUSH, not commit — the evidence requirement used to sit on `git commit`, which
  made every commit cost a full suite run and drove agents to one giant commit per feature
  (steering 8.34). A commit now only has to avoid bypassing the hook. `-n` is banned on
  commit only, deliberately: on `git push` it means `--dry-run`, which is harmless.
- `kiro-claim-before-worktree.sh` — `preToolUse` hook (matcher `execute_bash`) on the
  orchestrator. Exit code 2 BLOCKS creating the per-issue worktree
  (`git worktree add … issue-<N>`) until `issue claim-check <N>` confirms the issue is
  claimed in-progress on the remote — the mechanical enforcement of the deterministic
  claim. Fails open on any uncertainty (no issue number, no wrapper, or a claim-check
  error) so it never wedges a session.
- `kiro-issue-filing-gate.sh` — `preToolUse` hook (matcher `execute_bash`) on EVERY agent
  that can reach the tracker: the orchestrator plus `issue-intake-agent`,
  `product-management-agent`, `doc-reviewer-agent`, `dead-code-removal-agent`, and
  `issue-housekeeping-agent`. Exit code 2 BLOCKS an issue-CREATE call
  (`create-issue`, `issue create`) whose body is provably missing the provenance lines
  required by steering 8.32 (`Origin:`, `Subject:`, `Spawned-from:` for spawned issues,
  `Filing-rationale:`), and its block message hands the agent the fix-first evaluation
  instead. Read/update calls (`list-issues`, `get-issue`, `comment-issue`,
  `update-issue`, `issue claim-check`) pass untouched, and it fails OPEN whenever the
  body cannot be read (heredoc, command substitution, a variable, an unreadable
  `--body-file`, no jq/python available) so it never wedges a session. RESIDUAL: only the
  `execute_bash` matcher is wired; a create call issued through `executePwsh` is not seen
  (that matcher value is unverified against the Kiro docs, and an invalid matcher would be
  a worse failure than the gap). This is the mechanical half of the containment in 8.32 —
  the steering file, not the script, is the authority on what may be filed.
- `kiro-stop-gate.sh` — `stop` hook on the orchestrator and conductor. Blocks turn-end
  (via STDOUT `{"decision":"block","reason":"..."}`) while a spec is mid-implementation
  and the work is not honestly proven (a completed task with no evidence, a red latest
  capture, or a skipped/xfail dodge).
- `kiro-loop-gate.sh` — `stop` hook on the orchestrator. Blocks turn-end while the run
  is `IN_PROGRESS` with workable issues remaining and no recorded escalation, so the
  agent keeps working the backlog instead of asking "which issue next?".
- `red-for-right-reason.sh` — a helper the conductor/implementer call directly
  (`bash .kiro/hooks-bin/red-for-right-reason.sh <capture>`) to confirm a RED test
  failed on a genuine assertion, not an import/collection error.

> **Why a counter, not `stop_hook_active`:** Kiro's stop-hook event JSON has no
> `stop_hook_active` field (that is a Claude Code field). The two `stop` gates instead
> keep a per-run consecutive-block counter and allow the stop after a bounded number of
> consecutive blocks, so a session can never wedge. Any clean pass resets the counter.

- **The four-subagent cap is real.** The spec design-review panel (six reviewers) MUST
  be run in waves of at most four — the translated conductor/orchestrator prompts
  already instruct this; do not remove it.
- The leaf specialists' `toolsSettings.write.allowedPaths` are scoped per role
  (reviewers may write only to the spec dir + their own state; the implementer and
  merge reviewer may write to `src/`/`test/`). These per-agent path scopes are a Kiro
  capability with no Claude Code equivalent — keep them.

### 8A.4 Launch and usage

- **Interactive (confirmed):** start `kiro-cli` in the project, switch to the
  orchestrator (by name via the `/agents` picker, or its configured keyboard
  shortcut), and tell it to work the backlog. Switch to `spec-conductor` for a single
  feature/bugfix, or to any utility agent (`dead-code-removal-agent`,
  `doc-reviewer-agent`, `ci-workflow-agent`, `issue-intake-agent`, etc.) for a focused
  task.
- **Headless (provisional):**
  `kiro-cli chat --no-interactive --agent issue-work-orchestrator --trust-tools=read,grep,write "work the open-issue backlog"`,
  authenticated by `KIRO_API_KEY`. NOTE: the `--agent` flag for headless mode is NOT
  confirmed in the current public Kiro CLI docs — verify it against your installed
  `kiro-cli --help` before relying on it for automation; the interactive path above is
  the confirmed one.
- **Parallel runs on one machine:** run several `kiro-cli` instances, each in its OWN
  git worktree and with its OWN `KIRO_HOME` (Kiro's session store is keyed per
  directory but physically shares the global `~/.kiro` root; a distinct `KIRO_HOME` per
  run isolates it). This gives OS-process isolation that sidesteps the four-subagent
  cap entirely. The orchestrator's per-run registry/locks (8.27) and the
  never-move-local-`main` + `gc.auto 0` git rules (8.29) make sharing one clone safe.

### 8A.5 Reusable prompts (`.kiro/prompts/`) — the `/auto-work` equivalent

Kiro has NO user-defined `/name` slash commands (that is a Claude Code concept; see the
mapping table in Part 1). The equivalent surface is Kiro's **file-based prompts**: a
markdown file in `.kiro/prompts/` (workspace) or `~/.kiro/prompts/` (global), invoked in
`kiro-cli` chat with the **`@` prefix** — `@auto-work`, not `/auto-work`. Local prompts
override global ones of the same name and take precedence over same-named file references.
File-based prompts do NOT accept arguments (only MCP prompts do), which is fine for
`auto-work` — it takes none. `/prompts list`, `/prompts edit <name>`, and
`/prompts details <name>` manage them.

Install the never-stop autonomous backlog prompt, the counterpart of Claude Code's
`/auto-work` command (`ClaudeCodeSetupPrompt.txt` Part 13.1c):

```bash
mkdir -p .kiro/prompts
cp kiro-prompts/auto-work.md      .kiro/prompts/
cp kiro-prompts/continue-work.md  .kiro/prompts/
```

`@continue-work` is the recovery prompt for a run that stopped before the work was done: a
≤5-line status update, then it re-establishes its place from the on-disk state files
(verified against real git/issue/PR state — reality wins) and drives the recorded phase to a
terminal state, declaring void any instruction to interrupt, check in, summarize, or await
input. It is the bandaid for the behavior that the `continuous-work` steering rule (Part
8.33) is meant to prevent — needing it often means that rule is not loaded or not honored.
For a fully autonomous re-run the user can wrap it in Kiro's own loop:
`/goal continue to work until the current issue is implemented and closed` (default 5
iterations, `--max` to raise). `/goal` is recognized only at the start of user input, so it
cannot be invoked from inside a prompt file.

Then, with the `issue-work-orchestrator` agent active, type `@auto-work`. It runs the whole
backlog with no questions and no intermediate reports: the five non-negotiables are
(1) never ask which issue, (2) never stop, (3) claim on pick via the fail-closed
`issue start <N>` before fetching or branching, (4) always work the latest code (Remote
Sync at all six points, fresh issue list per iteration, every conflict to
`code-merge-reviewer`), (5) one worktree per issue under `.kiro/worktrees/issue-<N>/` with
full teardown. Non-negotiable #2 is enforced mechanically by `kiro-loop-gate.sh` (the CLI
`stop` hook), which blocks turn-end while `WORKABLE_ISSUES_REMAIN: yes` — subject to its
deliberate `LOOP_BLOCK_CAP` consecutive-block safety valve, after which the run must be
re-launched to continue.

On context exhaustion the prompt relies on Kiro's AUTOMATIC compaction (older history
replaced by a structured summary of goals/decisions/progress/next-steps while recent
messages stay verbatim; continuation is uninterrupted). It does NOT tell the agent to
compact itself: compaction is not agent-triggerable — it is automatic everywhere, and
manual `/compact` exists only in the CLI as a USER command (the IDE has no manual trigger
at all). Instead the prompt makes compaction lossless: checkpoint
`runs/<run-id>/resume_state.md` plus the registry heartbeat after every step, keep the
issue itself updated live, and re-read the state files immediately after a compaction
before acting. `inclusion: always` steering survives; `fileMatch` steering reloads when a
matching file is next touched. Compacted history is unrecoverable within the session, so
anything that must outlive it belongs on disk or on the issue. The CLI settings
`compaction.excludeMessages` and `compaction.excludeContextWindowPercent` (both default
`2`, the more conservative value winning) tune how much recent history stays verbatim.

#### 9.4 `git-workflow-shared.md` (steering — supports the next 3 hooks)
Place under `.kiro/steering/git-workflow-shared.md` with
`inclusion: manual` (referenced by hooks via `#[[file:...]]`):
```markdown
---
inclusion: manual
---
# Shared Git Workflow Steps

These steps are referenced by the git-commit, git-rebase, and git-push
hooks. The hooks share this content rather than each duplicating it.

## Step A: .gitignore compliance

Run `git status`. For each changed/untracked file decide whether it
belongs in the repository:
- DOES NOT belong: build artifacts, compiled output, cache dirs,
  IDE-specific files, temp files, secrets, credentials, env-specific
  files.
- DOES belong: source, configuration files (pyproject.toml,
  .pre-commit-config.yaml), docs, tests, scripts, CDK code, steering,
  hooks.

For each file that doesn't belong, add an entry to .gitignore (preserve
existing). Verify `git status` no longer lists ignored files.

## Step B: Integrate remote changes

`git fetch origin`. Compare local branch with origin: `git log HEAD..origin/<branch> --oneline`.
If remote changes exist:
1. Stash local uncommitted changes if any: `git stash`.
2. `git rebase origin/<branch>`.
3. On conflict: identify with `git diff --name-only --diff-filter=U`,
   read both versions of each file, produce a merged version that
   preserves both intents, `git add <file>`, `git rebase --continue`.
   Repeat until rebase completes.
4. If rebase becomes too tangled: `git rebase --abort`, fall back to
   `git merge origin/<branch>`.
5. Restore stash if applicable: `git stash pop` (resolve any conflicts
   the same way).

## Step C: Stage and commit

1. `git status` to review.
2. `git add <files>` for each file that should be committed.
3. `git diff --cached` — review what's about to be committed.
4. Generate a commit message:
   - subject in imperative mood, max 72 chars
   - blank line
   - body describing changes by component or purpose
5. `git commit -m "<message>"`.

A commit costs about a second (Step D), so commit at every natural boundary
rather than accumulating one enormous change. A readable series of small
commits is the deliverable (`ci-owns-the-test-suite.md`).

## Step D: Pre-commit hook handling

`git commit` triggers the pre-commit hook: ruff lint, ruff-format, bandit over
the staged files, and a secret scan. No tests, no mypy — under two seconds.
- Exit code 0: hook passed; proceed.
- Non-zero exit: fix every reported issue. Then go back to Step B
  (there may be new remote changes), Step C (stage fixes), Step D
  (commit again).
- NEVER use `--no-verify` to bypass the hook. There is nothing to save — and
  the secret scan is the one check whose miss cannot be undone after a push.

## Step E: Push (only used by git-push)

Push ONCE, when the batch of work is complete — not to find out whether it
works. `git push origin <branch>`. If rejected (non-fast-forward), go back to
Step B and retry. If a new branch needs upstream tracking:
`git push --set-upstream origin <branch>`.

`git push` triggers the pre-push hook: mypy, plus the FULL test suite if
CI-OUTAGE MODE is declared (`scripts/ci_outage_mode.py status`). Fix whatever
it reports; never `--no-verify`.

## Step F: Monitor CI (only used by git-push)

Determine host from `git remote get-url origin`. Use the project's
wrapper script (`scripts/github_wrapper.py` or `scripts/gitlab_wrapper.py`)
to fetch CI status — never `gh`/`glab`/`curl` (see
`use-git-wrapper-scripts.md`).

Wait for the pipeline to terminate. Apply the no-output-shortening rule to
every command. CI is where this project's test suite runs, and it is built not
to fail fast — so a red run is the COMPLETE list of what is wrong, not the
first thing wrong.

If the pipeline failed:
1. Retrieve the logs of EVERY non-successful job and enumerate every failing
   test and check before changing anything.
2. Group them by root cause and record `N failures across M jobs → K root
   causes`.
3. Fix every group (consult MCP doc servers and project docs as appropriate),
   committing as you go, then loop back to Step B and push ONCE.

Fixing one failure and re-pushing to discover the next is forbidden
(`ci-owns-the-test-suite.md`, `remote-ci-must-pass.md`).
```

### The CI capacity-fallback guide (INSTALL IT, always)

Copy it verbatim from this prompt's repository. Do this on setup, on migration, AND

literally in a different project would try to deploy a stack that does not exist.

   Then prove the split, because this is the assertion that regresses silently:

   ```

   among them. If it is, some hook is missing its `stages:` key (Part 2.2 step 1)
   and the project is back to running the suite on every commit.

   ruff-formatted at this scope, `--all-files` REWRITES the whole codebase (ruff

   destructive surprise mid-setup, and it buries the actual answer in a reformat
   diff. One already-clean file enumerates the same hooks and changes nothing.
   Confirm the inverse the same way — `pre-commit run --hook-stage pre-push
   --files README.md` lists mypy, and `pre-commit run --hook-stage manual pytest`
   is how the suite is invoked by hand.

### Reusable prompts (PART 8A.5)
`kiro-prompts/*.md` in the prompt repository → `.kiro/prompts/` (workspace) or
`~/.kiro/prompts/` (global). Invoked in `kiro-cli` chat as **`@name`** (NOT `/name` — Kiro
has no user-defined slash commands). File-based prompts take no arguments; local overrides
global overrides MCP. Managed with `/prompts list|edit|details`.
- `auto-work.md` → `@auto-work`: never-stop autonomous open-issue backlog run (the
  counterpart of Claude Code's `/auto-work`). The IDE reaches the same body through the
  `auto-work.kiro.hook` `userTriggered` hook (Part 9.4a), which reads the prompt file.
- `continue-work.md` → `@continue-work`: restart a run that stopped before the work was
  finished — status update, then continue to completion, with any interrupt/check-in
  instruction declared void (Claude Code counterpart: `/continue-work`). IDE hook: Part 9.4b.
  The behavioral fix that should make it unnecessary is the `continuous-work` steering rule
  (Part 8.33).

### Custom-agent hook trigger types (PART 8A, Kiro CLI agent JSON `hooks`)
Distinct from the Part 9 `.kiro.hook` triggers above. Keyed by trigger, each an array
of `{ "command", "matcher" }`:
| Trigger | Fires / effect |
|---|---|
| `agentSpawn` | when the agent starts; STDOUT (exit 0) is added to context |
| `userPromptSubmit` | on each user prompt |
| `preToolUse` | before a tool runs; **exit code 2 blocks** it (STDERR → the model) |
| `postToolUse` | after a tool runs (cannot undo it) |
| `stop` | at turn-end; blocks via STDOUT `{"decision":"block","reason":"..."}` |
